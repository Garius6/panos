# Known Issues

Найдено при разработке `demo/todo-app/` (нативный panos-бэкенд +
AOT-wasm фронтенд, реальный `сеть.http_запрос_sync` fetch). Не
исправлены — рабочие обходы использованы в демо-коде. Ранжировано по
серьёзности.

## 1. `для x в массив цикл` даёт elem-биндеру `nil` MIR-тип

**Исправлено 2026-08-02.** Fast-array lowering теперь назначает тип элемента
и одноимённому binder'у; добавлен WASM smoke-тест, проверяющий экспорт функции
с `для x в массив`.

`core/mir_lowering.odin:1648`, `lower_for_in_bind_names`:
`new_local(&ctx.b, names_syms[0], "", nil)` — хардкодит `nil` тип (и
пустое имя) для одноимённого случая `для x в массив цикл` (путь
`.Fast_Array`; `core/mir_lowering.odin:1564` — та же проблема у dst
`Get_Index_Instr`). Невидимо байткод-VM (не читает типы MIR-значений).
**Фатально для WASM AOT**: `is_wasm_phase1_function`
(`core/wasm_module.odin`) молча исключает ЛЮБУЮ функцию с таким
циклом из wasm-эмиссии — не ошибка компиляции, а "функция не найдена"
при попытке вызова. Баг общий (не wasm-специфичный), давно существует.

Обход в демо: index-range циклы (`для i = 0 по n-1 цикл` +
`.получить(i, запасное)`) — `For_Range` lowering не задет.

### Как исправить

Два места в `core/mir_lowering.odin`, оба внутри ветки `.Fast_Array`
`lower_for_in_stmt` (не трогать соседнюю ветку `.Iterator_Protocol` —
у неё СВОЙ, отдельный `nil`, см. ниже):

1. `core/mir_lowering.odin:1564` — `elem_v := new_value(&ctx.b, nil)`
   перед `Get_Index_Instr`. Тип элемента уже вычислим на этом месте:
   `iter_type := prune_type(ctx.tc.node_types[s.iterable])` (тип
   массива уже читается парой строк выше, в `iter_v_idx :=
   new_value(&ctx.b, ctx.tc.node_types[s.iterable])` — то же
   выражение, просто без `prune_type`) → `elem_v := new_value(&ctx.b,
   iter_type.element_type)`.
2. `core/mir_lowering.odin:1648` (`lower_for_in_bind_names`,
   однопеременная ветка) — `binder := new_local(&ctx.b,
   names_syms[0], "", nil)`. `lower_for_in_bind_names` уже получает
   `elem_v` параметром — у него теперь (после фикса №1) настоящий
   тип, читаемый через `value_type(&ctx.b, elem_v)` (та же helper-
   функция, что уже использует `emit_closure_value` в другом месте
   файла) → `new_local(&ctx.b, names_syms[0], "", value_type(&ctx.b,
   elem_v))`. Многопеременная ветка (деструктуризация `для (a, b) в
   ...`) ниже в этой же функции — судя по комментарию над функцией,
   `nil`-тип там ДОКУМЕНТИРОВАН как осознанный (см. `Let_Stmt`'s
   деструктуризация, тот же приём) — не трогать без отдельного
   решения.

`.Iterator_Protocol`-ветка (для `для x в итерируемое цикл` через
`.следующий()`) НЕ вызывает `lower_for_in_bind_names` из этого фикса
бесплатно — она передаёт `elem_v` из `Get_Variant_Field_Instr`, чей
`dst` тоже `new_value(&ctx.b, nil)` (`core/mir_lowering.odin` рядом с
`gvf.field_index = 0`). После фикса №2 эта ветка автоматически
получит настоящий тип В БИНДЕРЕ (через тот же `value_type(&ctx.b,
elem_v)`), но САМ `elem_v` (dst у `Get_Variant_Field_Instr`) всё ещё
`nil` — если что-то читает тип этого `Value_Id` ДО байндинга (не
похоже, но проверить), понадобится третий такой же фикс через
`next_result_type`/тип `Option`'а, уже вычисленный чуть выше в этой
ветке.

Проверка: собрать `demo/todo-app/frontend/main.ps` СО старым `для
задача в задачи цикл` (не index-range обходом) через `panos build
--target=wasm` — раньше падало тихо (`is_wasm_phase1_function`
исключает функцию), после фикса должно компилироваться. Плюс `just
test` (422 существующих — не должны сломаться, это чисто typing-фикс,
не поведенческий).

## 2. Кириллица в HTTP-путях никогда не матчится

**Исправлено 2026-08-02.** Native HTTP-мост percent-decode'ит путь перед
передачей в Panos; при ошибке декодирования сохраняет исходный путь.

`std/сеть/http.ps`'s router (`сопоставить_путь`/`Маршрутизатор`)
сравнивает сырой путь запроса без URL-decode. Любой HTTP-клиент
percent-encode-ит не-ASCII сегменты пути — маршрут `"/api/задачи"`
никогда не матчится с реальным запросом (`/api/%d0%b7%d0%b0...`).
Подтверждено curl: 404 на каждом кириллическом маршруте.

Обход: ASCII-маршруты (`/api/tasks`).

### Как исправить

Путь не декодируется НИГДЕ в цепочке — не в роутере, а на один уровень
ниже, в самом native-мосте. `core/vm_http_server_native.odin:132`:
`path_str = bridge_ctx.req.url.path` — это сырое поле из
провендоренного `external/odin-http`, само `odin-http` percent-decode
пути НЕ делает (только для query-параметров — см.
`external/odin-http/routing.odin:90`,
`query_get_percent_decoded`/`net.percent_decode`; путь — нет). Правка:

```odin
import "core:net"
...
decoded_path, decode_ok := net.percent_decode(bridge_ctx.req.url.path, context.allocator)
path_str = decoded_path if decode_ok else bridge_ctx.req.url.path
```

прямо на месте строки 132, ДО того, как `path_str` уходит панос-стороне
через `.путь()` (`core/vm_http_server_native.odin:353`). Это чинит
проблему для ЛЮБОГО потребителя `.путь()`, не только для
`Маршрутизатор` — `std/сеть/http.ps`'s `разбить_путь`/
`сопоставить_путь` (строки 365, 461) сами по себе трогать не нужно,
они уже сравнивают что получили, декодирование должно случиться раньше.

Проверка: `curl` на реальный кириллический маршрут (`/api/задачи` без
процент-кодирования curl'ом не пошлёт сам — нужно явно закодировать,
`curl 'http://host/api/%D0%B7%D0%B0%D0%B4%D0%B0%D1%87%D0%B8'`, либо
через реальный `fetch`/браузер, который кодирует автоматически) —
маршрут `р.получить("/api/задачи", ...)` должен теперь матчиться.

## 3. WASM AOT не умеет импортировать файловые std/-модули вообще

**Исправлено на уровне pipeline 2026-08-02.** `panos build --target=wasm`
теперь использует файловый module graph, пробрасывает `wasm_target` в
резолвер и лоурит общий `Mir_Module`; минимальная двухфайловая программа
с импортом собирается в WASM. `check_source` сохранён для no-FS сценариев.

Проверка `fixtures/json_fixture_main.ps` теперь проходит импорт, но
останавливается позже в независимом WASM stackifier bug (`br`-цель не найдена
среди открытых scope). Это уже не ограничение загрузчика модулей; импорт
`кодирование/json` станет практически применимым после исправления этого
backend-ограничения.

`core/pipeline.odin`'s `check_source` — "inline pipeline без файлового
I/O", никогда не резолвит реальные `импорт "путь"` `.ps`-файлы (только
синтетические builtin-модули типа DOM/строки/сеть). Весь WASM AOT
backend тестировался только через `check_source` — значит **ни одна
программа, компилируемая в wasm сегодня, не может заимпортировать
реальную std/-библиотеку** (`json.ps`, `коллекции.ps`, что угодно ещё).

Заблокировало использование `json.ps`/`коллекции.ps` во фронтенде
демо; пришлось написать ручной, специфичный под формат бэкенда JSON-
парсер (`demo/todo-app/frontend/main.ps`, `извлечь_сырое_значение` —
не полноценный парсер, не обрабатывает экранированные кавычки).

### Как исправить

Хорошая новость: почти весь механизм для этого уже существует, просто
не подключен на wasm-стороне. Нативный путь (`main.odin:64-99`, `run_file`)
УЖЕ умеет "многофайловая программа → один объединённый модуль":

```
graph := core.load_module_graph(filename)          // резолвит импорты, читает файлы
results := core.resolve_and_typecheck_all(&graph)   // resolve+typecheck на весь граф
module := core.lower_program_graph(results)         // → ОДИН Mir_Module
global_registry := core.lower_module_to_bytecode(&module)
```

`panos build --target=wasm` (`main.odin`'s `run_build`, добавлен только
что) сегодня идёт другим, однофайловым путём (`core.check_source` →
`core.lower_module` на РЕЗУЛЬТАТЕ одного файла), потому что именно этот
путь никогда не трогает файловую систему — нужен для WASM-инструментов
без FS (LSP, браузерный REPL) и был единственным существовавшим до
`build`. Задача — дать `run_build` ВЫБОР пути, не сломав ту причину,
по которой `check_source` вообще существует.

Шаги:

1. `core/module_loader.odin:145` — `resolve_and_typecheck_all` сегодня
   жёстко зовёт `resolve_module(graph, module)` (без wasm_target,
   т.е. всегда `false`). Добавить параметр:
   `resolve_and_typecheck_all :: proc(graph: ^Module_Graph, wasm_target: bool = false) -> [dynamic]Module_Result`,
   пробросить в `resolve_module(graph, module, wasm_target)` (строка
   156). `wasm_target` уже проведён через `resolve_module`/
   `new_module_resolver_ctx` (`core/resolver.odin:659,960`) — просто
   не из этой функции сегодня.
2. `main.odin`'s `run_build` — вместо `core.check_source(source, true)`
   использовать граф-путь:
   ```odin
   graph := core.load_module_graph(input)
   results := core.resolve_and_typecheck_all(&graph, true) // wasm_target=true
   // диагностики — тот же паттерн, что print_diagnostics_and_exit (строка 52),
   // но собранные из graph.parse_diagnostics + каждого results[i].{res_ctx,tc_ctx}.diagnostics
   module := core.lower_program_graph(results)
   bytes := core.lower_module_to_wasm(&module)
   ```
   Диагностики теперь приходят с несколькими `file_id`/`Module_Graph`
   (как у `print_diagnostics_and_exit`), а не с одним `source`-текстом —
   переиспользовать эту функцию напрямую (она уже принимает `^Module_Graph`),
   вместо ручного `span_line_col(source, ...)` из текущей однофайловой
   версии.
3. `check_source` (`core/pipeline.odin:106`) и однофайловый режим
   ОСТАВИТЬ как есть — он нужен LSP/no-FS сценариям. Не удалять, не
   менять сигнатуру.
4. Открытый вопрос, требующий отдельной проверки перед тем как считать
   фикс завершённым: `is_wasm_phase1_function`/весь `core/wasm_module.odin`
   писался и тестировался ИСКЛЮЧИТЕЛЬНО через однофайловый `check_source`
   — не факт, что он корректно обрабатывает `Mir_Module`, пришедший из
   `lower_program_graph` (многомодульный) без доп. правок (напр. если
   там есть код, неявно предполагающий "один файл = весь module_graph").
   Стоит собрать маленькую 2-файловую (`импорт`) fixture-программу и
   прогнать `panos build --target=wasm` на ней ПЕРВЫМ шагом проверки,
   прежде чем переключать `demo/dom`/`demo/todo-app` на новый путь.

Проверка: `demo/todo-app/frontend/main.ps` (после фикса) должен суметь
`импорт "кодирование/json"`/`импорт "коллекции"` — заменить ручной
JSON-парсер (`извлечь_сырое_значение`) на `json.разобрать`/`.поле(...)`,
убрать комментарий-документацию про ограничение (строки 5-23) как
устаревший.

## 4. Два гэпа в выводе типов

- `выбор получить() ... конец` напрямую (без промежуточной типизированной
  привязки) не выводит тип `получить()` — `Type Error: выбор ожидает
  значение перечисления... получено '?N'`. Работает только через
  `пер x: T = получить()` + матч на `x`.
- `массив()` внутри `выбор`-arm'а не выводит тип элемента, даже когда
  окружающая функция явно объявляет `-> Массив(T)`. Нужна явная
  локальная привязка `пер x: Массив(T) = массив()` снаружи матча.

### Как исправить

Второй пункт — корень найден: `check_expr` (`core/type_cheker.odin`)
не имеет ветки `case ^Match_Expr:` вообще (проверено — её нет в файле),
поэтому `выбор ... конец`, когда бы он ни встретился, ВСЕГДА идёт через
безусловный `infer_match_expr` (чистый inference, без ожидаемого типа)
и только ПОТОМ сверяется с `expected_type` снаружи — то есть тело arm'а
(`массив()` внутри) инферится без контекста в принципе, контекст
появляется слишком поздно. Сравни с `^Array_Expr`, у которого такая
ветка ЕСТЬ (`core/type_cheker.odin:3913`) и она правильно прокидывает
`expected_type.element_type` в пустой массив. `^If_Expr` (если-как-
выражение) в check_expr'е тоже НЕТ — похоже, это не match-специфичный
баг, а общий пробел: expected-type contextual propagation реализована
только для нескольких literal-форм (Array/Map/Lambda/бинарные `Plus`
и т.п.), не для join-точек типа match/if. Фикс — добавить
`case ^Match_Expr:` в `check_expr`, которая для каждого arm'а вызывает
`check_expr(ctx, arm_tail_expr, expected_type)` вместо текущего
`infer_expr` внутри `infer_match_expr`; аккуратно — `infer_match_expr`
переиспользуется и для случаев БЕЗ ожидаемого типа (top-level стейтмент),
так что новая ветка в check_expr должна быть ДОПОЛНИТЕЛЬНЫМ путём, не
заменой существующего.

Первый пункт (`выбор получить()` напрямую) — репро из этой сессии не
сохранено как минимальный fixture (в финальном демо-коде везде уже
стоит обходной путь), и есть основания думать, что для quалифицированных
паттернов (`Тип.Вариант(...)`) это уже работает — см. специальный
разбор `InferVar`-subject в `infer_match_expr`
(`core/type_cheker.odin:~6285`, ищет `ctor.module_name != ""`). Прежде
чем чинить — воспроизвести заново минимальным примером (актёр,
`получить()` напрямую в `выбор`, БЕЗ обходной `пер`-привязки) и
убедиться, что баг вообще ещё актуален для КВАЛИФИЦИРОВАННЫХ паттернов
(а не только для неквалифицированных, что было бы ожидаемым поведением
по дизайну, судя по комментарию в коде).

## 5. `длина(x)` vs `.длина()` — путающий сплит

**Исправлено 2026-08-02.** Для попытки вызвать метод у `Строка` typechecker
теперь объясняет, что строки не имеют методов, и подсказывает `строки.имя(x)`.

`длина(x)` — глобальный полиморфный builtin (Строка/Массив/
Соответствие). `.длина()` — отдельный метод, существует ТОЛЬКО на
Array_Value/Map_Value — **у Строки метода `.длина()` нет вообще**.
Вызов `текст.длина()` даёт "Type Error: попытка получить поле у
не-структуры (тип: Строка)" — путающее сообщение про "field access"
вместо "метод не найден"/"имели в виду `длина(x)`?".

### Как исправить

Строка вообще не поддерживает методы (`.имя()`) — только
модуль-квалифицированные функции (`строки.длина_байт(x)` и т.п.), это
осознанный дизайн. Правильный фикс — не добавлять `.длина()` на
Строку (отдельный, больший дизайн-вопрос про метод-синтаксис на
примитивах), а улучшить сообщение там же, где уже есть прецедент для
Array/Map.

`core/type_cheker.odin:6546-6552` уже даёт кастомное сообщение для
`obj_type.kind == .Array || obj_type.kind == .Map`:
```odin
} else if obj_type.kind == .Array || obj_type.kind == .Map {
	return report(ctx, e.span, "Type Error: метод коллекции '%s' нужно вызвать через ()", e.property)
```
Добавить симметричную ветку ПЕРЕД финальным `else` (строка 6567,
`попытка получить поле у не-структуры`):
```odin
} else if obj_type.kind == .String {
	return report(
		ctx, e.span,
		"Type Error: у Строки нет методов — используйте строки.%s(x, ...)",
		e.property,
	)
```
`e.property` (запрошенное имя) подставляется прямо в подсказку, даже
если такой функции в `строки.*` нет — просто указывает верное
направление, не проверяет существование.

Проверка: `"текст".длина()` — раньше "поле у не-структуры", теперь "у
Строки нет методов — используйте строки.длина(x, ...)".

## 6. `строки.найти` (рановый индекс) vs `строки.срез_байт`/`строки.длина_байт` (байтовый) — скрытая порча текста

**Документировано 2026-08-02.** Предупреждение добавлено рядом с builtin-
регистрацией и в документацию; отдельные типы индексов остаются будущей
архитектурной задачей.

`строки.найти` возвращает РАНОВЫЙ индекс. `строки.срез_байт`/
`строки.длина_байт` берут/возвращают БАЙТОВЫЙ индекс. Оба типизированы
как обычный `Целое` — ничего не мешает смешать. Для ASCII совпадает
случайно; для кириллицы (2 байта/символ в UTF-8) расходится, и срез по
не-рановой границе молча портит текст. Подтверждено реальным падением:
"купить хлеб" → "купит�" (Playwright-тест поймал).

Обход: везде рановые `строки.срез`/`длина(x)`, парой с `строки.найти`.

Стоит рассмотреть: отдельные типы для ранового/байтового индекса
(превратить класс бага в type error), либо явная документация-
предупреждение на `строки.найти`/`строки.срез_байт`.

### Как исправить

Отдельный тип для индекса (напр. `РановыйИндекс`/`БайтовыйИндекс`
как distinct-обёртки над `Целое`) — правильное решение долгосрочно, но
это меняет сигнатуры ВСЕХ существующих вызовов `строки.найти`/
`строки.срез`/`строки.срез_байт` по всей кодовой базе (`std/`,
`panosiki/*`, фикстуры) — крупная, ломающая правка, не "one-sitting"
несмотря на приоритет в списке. Для быстрого фикса вместо этого:
задокументировать явно в двух местах.

1. `core/stdlib.odin` — рядом с регистрацией `"строки::найти"` (строка

## 7. Каскад непонятных ошибок при multi-statement match-arm без `тогда...конец`

**Исправлено 2026-08-02.** Парсер сначала сообщает целевую ошибку, если после
однострочного тела нет разделителя и остаётся код на той же строке.

Уже известное ограничение (см. память `reference_panos_language_gotchas`
— лимит в одно выражение на arm, нужен `тогда...конец` для нескольких
стейтментов). Забытый `тогда`/`конец` даёт длинный каскад несвязанных
на вид ошибок парсера вместо одной понятной диагностики.

### Как исправить

Место: `core/parser.odin:2954-2966`, `parse_match_expr`'s однострочная
(`-> выражение`) ветка — парсит РОВНО один statement, затем `for {
... break }` вырожденно всегда прерывается после первой итерации.
Проблема — то, что происходит СРАЗУ ПОСЛЕ: цикл выше (`for peek_token
!= .End && != .EOF`) просто идёт на следующую итерацию и пытается
распарсить очередной `arm.pattern = parse_pattern(p)` из ОСТАВШЕГОСЯ
на той же строке кода — отсюда каскад ("ожидалось Arrow, обнаружен
Ident" и т.п., это ошибки парсинга ПАТТЕРНА из текста, который на
самом деле — второй statement забытого multi-line arm'а).

Парсер зависит от отсутствия backtracking (сам комментарий над этим
кодом это объясняет — грамматика паттерна `a.b(...)` неотличима от
statement'а), так что честно разобрать "что тут было" нельзя. Но можно
поймать САМ ПРИЗНАК ошибки дёшево: легитимная СЛЕДУЮЩАЯ ветка ВСЕГДА
начинается на НОВОЙ строке (человек естественно пишет один паттерн на
строку); если после разбора single-statement arm'а следующий токен НЕ
`.End`/`.EOF` И не имеет `nl_before` (тот же флаг токена, что уже
использует `infix_bp`-вызывающий код, `core/parser.odin` рядом с
`if op.kind == .LParen && op.nl_before do break`) — значит на этой же
строке осталось что-то ещё, почти наверняка второй statement
забытого `тогда...конец`. Вставить проверку сразу после `break` в
Arrow-ветке (перед `arm.span = span_from(...)`):

```odin
nxt_tok := peek_token(p.stream)
if nxt_tok.kind != .End && nxt_tok.kind != .EOF && !nxt_tok.nl_before {
	report_parse(p, nxt_tok.span,
		"Синтаксическая ошибка: несколько выражений в одной строке ветки выбор — используйте 'тогда ... конец' для нескольких операторов")
}
```
(не `return`/не прерывать парсинг совсем — просто ОДНА явная
диагностика ДО того, как парсер уйдёт в каскад; остальной цикл может
продолжить как раньше, лишние диагностики от каскада всё равно
неизбежны, но первая и главная будет понятной).

Проверка: тестовый фикстур с забытым `тогда`/`конец` на multi-statement
arm'е — первая строка diagnostics теперь должна быть про "несколько
выражений в одной строке", не про "ожидалось Arrow".

## 8. MIR-построение УЖЕ унифицировано между таргетами — расхождения только до/после

Вопрос "унифицировать формирование MIR для обоих таргетов" разобран
2026-07-30: сам `lower_module` (`core/mir_lowering.odin:79`) уже
target-agnostic, без единой ветки на wasm/native — унифицировать
нечего. Реальные различия — по краям:

**До MIR (frontend/resolve)**:
- Вход в пайплайн разный — native: `load_module_graph`+
  `resolve_and_typecheck_all`+`lower_program_graph` (многофайловый,
  реальный `импорт`); wasm: `check_source` (однофайловый inline, без
  module_loader) — это и есть #3 выше, самое крупное расхождение.
- `Resolver_Ctx.wasm_target` bool (`core/resolver.odin:447`) —
  единственная реальная ветка ВНУТРИ резолва: `внешний`-декларации
  на native делают eager `dynlib.load_library`/`symbol_address`, на
  wasm — пропускают.

**После MIR (consumption одного и того же `Mir_Module`)**:
- `lower_module_to_bytecode` (native) берёт весь `Mir_Module` без
  фильтрации.
- `lower_module_to_wasm` фильтрует ПОФУНКЦИОНАЛЬНО через
  `is_wasm_phase1_function`/`is_wasm_phase1_type`
  (`core/wasm_module.odin:92-116`) — белый список типов
  (`Number/Integer/Bool/Void/String/Struct/Array/Enum/Map/Error/
  Tuple/Function/Interface`), явно исключены `.Process` (акторы —
  см. [[project_panos_wasm_actors_cps_design]]), `.Pointer`, любой
  `nil`-тип (сюда падает баг #1). Исключение ТИХОЕ — функция просто
  не попадает в вывод, не ошибка компиляции.

Вывод: унификация не нужна на уровне MIR; нужна на краях — #3 (вход)
и #9 ниже (выход, но по-другому — не через типы функций, а через
явную таблицу доступности конкретных builtin'ов).

## 9. Идея: compile-time таблица доступности builtin'ов по таргету (вместо runtime panic / silent exclusion)

**Исправлено 2026-08-03.** `core/builtin_availability.odin` — единый
источник правды для native-only, AOT-WASM-only и общих builtin'ов.
Typechecker читает таблицу через `wasm_target`, а bytecode VM использует её
в синхронном и асинхронном dispatch как defense-in-depth. Opaque-методы
нативных ресурсов и акторы не являются builtin-вызовами и остаются
отдельными задачами.

Сегодня несовместимость модуля с таргетом обнаруживается ПОЗДНО и
по-разному:
- Native VM: `DOM::*`/`сеть::http_запрос_sync` (wasm-only) —
  `fmt.panicf` в рантайме (`core/vm.odin:1037-1046`).
- WASM backend: `время.спать_мс`, `ос.выполнить`, `фс.*` (часть),
  `бд.*`, HTTP-сервер, `внешний`-FFI, `сжатие.*`, `синтаксис.*`
  (native-only) — паникуют в соответствующих `core/vm_*_wasm.odin`
  файлах при вызове.
- Акторы (`Процесс(T)`/`запусти`) на wasm — вообще без паники, тихо
  исключаются из вывода целиком (`is_wasm_phase1_function`, см. #8).

Предложение: небольшая статическая таблица (имя builtin'а/модуля →
`{нативный, wasm, оба}`), проверяемая на этапе typecheck через
`ctx.res.wasm_target` — поле уже есть в `Resolver_Ctx`
(`core/resolver.odin:447`) и уже доступно из `Type_Ctx` через
`ctx.res` (используется для `внешний`), просто пока никто не читает
его в `core/type_cheker.odin` для builtin-вызовов. Превращает
runtime-панику/тихое исключение в обычную `Type Error` НА МЕСТЕ
вызова, до запуска — тот же принцип, что typecheck уже применяет
везде остальные.

Открытый вопрос (не решён, требует отдельного архитектурного
решения перед реализацией — см. `feedback_ask_before_architecture_
decisions`): куда класть источник правды.
- (а) Центральная таблица в typechecker, существующие
  runtime-панические guards в `vm.odin`/`*_wasm.odin` остаются как
  defense-in-depth (не должны срабатывать после фикса, но не
  удаляются).
- (б) Генерировать panic-guards ИЗ той же таблицы — чище (один
  источник правды), но требует рефакторинга существующих guard'ов,
  не только добавления нового кода.

Акторный случай (#8, `.Process`) в эту таблицу НЕ укладывается
напрямую — это не единичный builtin, а целый ТИП, инфицирующий любую
функцию, что его использует (транзитивно) — там нужна отдельная
диагностика уровня "эта функция не может быть скомпилирована в wasm,
потому что использует акторы" на самой границе `is_wasm_phase1_
function`, а не в таблице builtin-вызовов.

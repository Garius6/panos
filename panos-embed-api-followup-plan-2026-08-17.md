# План: доработка `panos_embed` (`zig/embed.zig`) — устранение пробелов ревью

Снапшот 2026-08-17. `panos_embed` (`zig/embed.zig`, ~240 строк) — первый
публичный API встраивания Panos в нативный Zig-хост (игровой движок и
т.п.), добавлен в отдельном коммите (`9609995`, "feat: add embeddable
Zig runtime"), задокументирован в `docs/src/architecture/embedding.md`.
Ревью ядра (жизненный цикл `Runtime`, владение памятью, `внешний
"хост"` C-ABI мост) — сделано аккуратно, headline-фича протестирована
e2e (`tests/embed_host_test.zig`). Ниже — 4 реальных, конкретных
пробела, найденных при ревью, каждый со своим планом. Это НЕ
реализация — план для передачи другому агенту.

Приоритет (см. секции ниже за деталями): **1 → 2 → 4 → 3** (см.
обоснование в конце).

---

## 1. Рендер диагностик недоступен из `panos_embed`

**Проблема**: `panos_core.diagnostic.Diagnostic` несёт только `message`
+ `severity` + `span{file_id, start: u32, end: u32}` (байтовые офсеты,
`zig/core/diagnostic.zig:19-23`) — НЕ готовую строку. Рендер в
`путь:строка:колонка: сообщение` формате (`formatDiagnostic`,
`writeGraphDiagnostics`/`writeModuleDiagnostics`) живёт в `zig/cli/
main.zig:14-88` — это исходник ИСПОЛНЯЕМОГО файла CLI (`root_source_
file` в `build.zig`), НЕ модуль `panos_core`/`panos_embed`. Хост,
импортирующий `panos_embed` (`build.zig`'s `addImport("panos_embed",
...)`), физически не может дотянуться до `cli/main.zig`'s функций —
они не экспортируются никаким модулем, это отдельная единица сборки.
Значит хост обязан САМ переизобрести byte-offset→line/column рендер
(`source.SourceFile.lineColumn`, `zig/core/source.zig:46`, уже есть,
но тоже не переэкспортирован через `panos_embed`) — реальная,
конкретная дыра, не гипотетическая.

**План**:
1. Переместить `formatDiagnostic`/`writeGraphDiagnostics` (или их
   логическую суть) из `zig/cli/main.zig` в `panos_core` — естественное
   место: рядом с `panos_core.diagnostic`, например новая функция
   `diagnostic.format(allocator, file: source.SourceFile, value:
   Diagnostic) ![]u8` (та же сигнатура, что сегодняшний
   `cli/main.zig:formatDiagnostic`, строки 14-32 — перенести тело
   почти без изменений, `DiagnosticFormatError` тоже переехать в
   `panos_core.diagnostic`).
2. `zig/cli/main.zig` — заменить свою копию на вызов
   `panos_core.diagnostic.format(...)`, убедиться что `zig build test`
   зелёный (существующие CLI-тесты на формат диагностик не должны
   измениться побайтово).
3. `zig/embed.zig` — добавить публичный ре-экспорт, симметрично
   существующему `pub const Value = panos_core.value.Value;`/
   `pub fn renderValue(...)` (строки 159-164): например
   `pub const formatDiagnostic = panos_core.diagnostic.format;` +
   опционально удобный helper `Runtime.formatDiagnostics(self, writer,
   diagnostics) !void`, который сам находит нужный `SourceFile` через
   `self.graph_state.moduleForFile(span.file_id)` (та же логика, что
   `writeGraphDiagnostics` уже делает в `cli/main.zig:70-84` — тоже
   стоит перенести целиком, не только низкоуровневый `format`, чтобы
   хосту не пришлось самому писать fallback на "файл не найден").
4. Тест: в `tests/embed_test.zig` (или новый `tests/embed_
   diagnostics_test.zig`) — граф с намеренной type-ошибкой, вызвать
   новый `Runtime.formatDiagnostics`, проверить что строка содержит
   `путь:line:col:` в ожидаемом формате (не просто "не упало").

Даёт ОДИН источник правды для рендера диагностик (CLI и embed-хосты
дальше не расходятся) — попутно чинит текущее дублирование (`cli/main.
zig`'s `formatDiagnostic` уже приватная копия того, что должно быть в
`panos_core`).

## 2. Нет reload/reset API — `Runtime` строго one-shot

**Проблема**: `Runtime.load()` возвращает `error.AlreadyLoaded`, если
`stage != .empty` (`zig/embed.zig:60`) — единственный способ загрузить
ДРУГОЙ (или тот же, изменённый) скрипт — полный `deinit()` + новый
`init()`. Для игрового хоста с hot-reload сценариев (обычный кейс при
разработке — правишь `.pns`, хочешь увидеть эффект без перезапуска
всего процесса/уровня) сегодня нет пути короче "выбросить весь Runtime
целиком, включая уже скомпилированные соседние модули, даже если
поменялся один файл".

**Открытая развилка** (решить перед реализацией — реальный
архитектурный выбор, не мелочь):
- **(a) `Runtime.reset()`** — деструктурит `graph_state`/
  `compiled_graph`/`machine`, возвращает `stage = .empty`, тот же
  `allocator`/`config` переиспользуются, `load()` можно звать заново.
  Дёшево реализовать (по сути тело текущего `deinit()` минус
  `self.* = undefined` в конце), НО семантически хост должен понимать,
  что старый `machine.output`/любые Value из предыдущей загрузки
  становятся невалидны сразу — тот же контракт, что уже
  задокументирован для "valid until next call", просто теперь
  "или до reset".
- **(b) Оставить строго one-shot, задокументировать паттерн явно** —
  "для hot-reload держите пул/пересоздавайте Runtime" — ноль нового
  кода, просто закрыть вопрос как "не баг, осознанный дизайн" в доках
  (`docs/src/architecture/embedding.md`). Дешевле, но перекладывает
  boilerplate (пересоздание `global_search_roots`/`program_args`
  конфига при каждом реlоаде) на каждого хоста.

**Рекомендация**: (a), если реализация окажется дёшева (весь нужный
код уже есть в `deinit()`, разница — не звать `self.* = undefined` и
не финализировать `allocator`-владение) — маленький, явно полезный
довесок. Проверить перед стартом: не остаётся ли что-то из `Config`
(в частности `global_search_roots`/`program_args`, которые Runtime не
владеет, только держит ссылку) в невалидном состоянии после `reset()`
— судя по коду, `Runtime` их не копирует, только ссылается, так что
`reset()` их не трогает вообще — должно быть безопасно.

**План** (если выбрано (a)):
1. `zig/embed.zig`: `pub fn reset(self: *Runtime) void` — деинициализирует
   `machine`/`compiled_graph`/`graph_state` (то же тело, что `deinit()`,
   БЕЗ `self.* = undefined`), затем переинициализирует `graph_state`
   заново (`panos_core.module_loader.Graph.init(self.allocator)` +
   восстановить `global_search_roots` из сохранённого `Config` — значит
   `Runtime` должен ХРАНИТЬ исходный `Config` целиком, не только
   `program_args`/`foreign_profile_enabled` по отдельности, как сейчас
   — небольшой рефакторинг полей структуры), `stage = .empty`.
2. Тест: загрузить скрипт A, вызвать `обновить`, `reset()`, загрузить
   ДРУГОЙ скрипт B с другим экспортом, убедиться что B работает и что
   A-специфичные экспорты больше не резолвятся (`call` на старое имя
   возвращает `error.ExportNotFound`, не крашится/не находит старое).
3. `docs/src/architecture/embedding.md` — секция "Жизненный цикл
   сценария" дополняется примером hot-reload через `reset()`.

## 3. Нет capability/sandboxing knob для недоверенного скрипт-контента

**Проблема**: `Runtime` не даёт способа ограничить, какие native-only
builtin'ы (`внешний`, `ос.выполнить`, `фс.*`, `бд.*`, HTTP-сервер)
доступны загруженному скрипту. Сегодняшний пример в доках — доверенный
игровой скрипт (сам хост его пишет/шипит), для которого это не
проблема. Но если хост когда-нибудь захочет пустить СТОРОННИЙ контент
(моды от игроков) через `panos_embed` — сегодня нет механизма это
ограничить. Тот же класс риска, что обсуждался для `pan`-хуков
(см. `panos-fat-binary-full-library-bundling-plan-2026-08-17.md`
соседний файл, там про build-hooks зависимостей — здесь про
runtime-контент, но принцип общий: явный allowlist, не implicit trust).

**Статус**: НЕ заявлен как use-case в текущих доках (`embedding.md`
явно про доверенный игровой код) — это **расширение scope**, не баг
сегодняшней реализации. Требует отдельного архитектурного решения
ПЕРЕД тем, как писать код (см. `feedback_ask_before_architecture_
decisions` — этот пункт особенно подходит под "surface the fork,
don't decide unilaterally").

**Открытые вопросы для обсуждения (не решать в одиночку)**:
- Где живёт allowlist/blocklist — `Runtime.Config` (новое поле,
  например `capability_profile: enum { trusted, sandboxed }` или
  точечный список разрешённых модулей) — или это должно быть решено
  на уровне `target_policy`/`Resolver`, тем же местом, что уже
  различает `wasm_target`/`.native` (`project_panos_mir_qbe_backend`
  память упоминает `target_policy.TargetProfile` — проверить, есть ли
  там уже подходящий крючок, прежде чем заводить новый параллельный
  механизм).
- Насколько глубоко резать — полный запрет `внешний`/`ос.*`/`фс.*`
  разом (проще, грубее) vs гранулярный per-builtin список (гибче,
  сложнее поддерживать в актуальном состоянии по мере роста стандартной
  библиотеки).
- Существующий `core/builtin_availability.odin`-эквивалент в Zig-коде
  (Odin-эра память упоминает "compile-time таблица доступности
  builtin'ов по таргету", `ИСПРАВЛЕНО 2026-08-03` в `ISSUES.md` — если
  портирован в Zig, это готовый механизм для third-value
  `.native_sandboxed` профиля; если НЕ портирован — придётся сначала
  проверить, пережила ли эта таблица Zig-миграцию).

**Рекомендация**: не начинать реализацию, пока не подтверждён реальный
хост, которому это нужно (сегодня гипотетический use-case) — держать
как задокументированный, осознанно отложенный пробел, а не активную
задачу. Приоритет ниже пунктов 1/2/4.

## 4. Тестовое покрытие — только happy-path

**Проблема**: `zig/embed.zig`'s собственный тест (строки 189-240) и
`tests/embed_host_test.zig` вместе дают 2 теста, оба happy-path.
Непокрыто:
- `hasGraphErrors()`/`hasCompilationErrors()` ветки — намеренно
  сломанный скрипт (синтаксическая или type-ошибка), убедиться что
  `runtime.load()`/`.compile()` НЕ бросают Zig-error (по контракту
  документации — они возвращают диагностики через отдельные
  геттеры), а `call`/`runStart` после этого возвращают `error.
  NotRunnable`/`error.NotCompiled`, не крашатся.
- Повторный `call()` после того, как ОДИН вызов вернул
  `.runtime_error` (панику внутри скрипта) — Runtime должен остаться
  в рабочем состоянии для следующего вызова (или явно задокументировано
  обратное, если это не так — сегодня не проверено ни тестом, ни
  доками).
- `Runtime.call()` с несуществующим именем экспорта —
  `error.ExportNotFound` (сегодня есть в коде, `zig/embed.zig:116`, но
  нет теста, что он реально возвращается, а не паникует раньше).

**План**: 3-4 новых `test` блока в `zig/embed.zig` (рядом с уже
существующим) или в `tests/embed_test.zig`, каждый — маленький,
целенаправленный, без новой инфраструктуры (переиспользовать
`MemoryReader`, уже есть в обоих файлах).

## Приоритизация и обоснование

1. **Диагностики (#1)** — самый дешёвый и самый нужный: любой реальный
   хост, показывающий игроку/девелоперу ошибку скрипта, упрётся в это
   на первом же кривом `.pns`-файле. К тому же чинит уже существующее
   дублирование кода (`cli/main.zig` не должно держать приватную копию
   логики, которая логически принадлежит `panos_core`).
2. **Тесты error-путей (#4)** — дёшево, ловит регрессии в контрактах,
   которые уже задокументированы, но не гарантированы тестами.
3. **Reset/reload (#2)** — реальная, но не блокирующая фича; ценность
   зависит от того, действительно ли есть hot-reload use-case у первого
   реального хоста (Codex, судя по формулировке задачи — “embed panos в
   проекты” — уточнить, нужен ли hot-reload, прежде чем тратить время).
4. **Sandboxing (#3)** — architecturally самый крупный кусок, явно
   отложен до появления реального untrusted-content use-case; заводить
   отдельным plan-mode проходом когда/если понадобится, не сейчас.

## Вне рамок этого плана

- Смена самой модели владения `Runtime`/GC (mark-sweep, stop-the-world)
  — вне scope, `panos_embed` лишь оборачивает существующий `vm.Vm`, не
  меняет его внутреннюю модель.
- Многопоточное использование одного `Runtime` из нескольких потоков
  хоста одновременно — не заявлено, не проверялось; если понадобится,
  отдельный вопрос (нужен ли `Runtime` per-thread, или внутренняя
  синхронизация) — не предполагать ответ заранее.

# План: fat binary — полная упаковка `внешний`-библиотек, без рантайм-зависимости от OS loader

Снапшот 2026-08-17. Цель: `panos build --compile` сегодня упаковывает
ТОЛЬКО path-style `внешний "./lib.so"` библиотеки; голые
(bare-name) `внешний "raylib"` — НЕ упаковываются, на рантайме
резолвятся через обычный OS loader search (`LD_LIBRARY_PATH`/
`DYLD_LIBRARY_PATH`/rpath/системные пути) — то есть standalone-бинарник
сегодня НЕ standalone для программ с bare-name FFI. Задача — упаковать
байты этих библиотек тоже, чтобы бинарник на целевой машине не зависел
от того, что там установлено.

Это НЕ реализация — план для передачи другому агенту. Разделён на
"залоченные решения" (можно начинать без дополнительных вопросов) и
"открытые развилки" (нужно подтверждение перед стартом — см.
`feedback_ask_before_architecture_decisions` в памяти этого проекта:
архитектурные развилки поднимать явно, не решать молча).

---

## Текущее состояние (проверено по коду, не по памяти)

- `zig/core/bundle.zig` `collect()` (строка 80) обходит весь
  `module_loader.Graph`, для каждого модуля ищет `внешний`-декларации.
  `foreign.library` без `/` (bare name) — **пропускается целиком**
  (строка 112: `if (std.mem.indexOfScalar(u8, foreign.library, '/') == null) continue;`,
  с комментарием "resolved via the OS loader's own search path, not a
  project-relative file; nothing to embed").
- Path-style (`"./lib.so"`) резолвится через
  `resolver.resolveForeignLibraryPath` (`zig/core/resolver.zig:254`) —
  чистая функция, путь считается ОТНОСИТЕЛЬНО файла, где написан
  `внешний`, читается с диска (`readFileAlloc`), кладётся в bundle с
  ключом через `bundleKey`.
- На рантайме (`zig/cli/main.zig` `runFatBinary`, строка 602): bundle
  распаковывается, `.pns`-контент отдаётся из памяти
  (`bundle.BundleReader`), а `is_library`-записи пишутся на РЕАЛЬНЫЙ
  диск во временную директорию `.panos-fat-<timestamp>/` — потому что
  `dlopen`/`LoadLibraryW` требуют реальный файл. Дальше
  ВЕСЬ пайплайн (`runtime.load`→`runtime.compile`→`runtime.runStart`)
  перезапускается заново с нуля на КАЖДОМ старте фат-бинарника
  (см. `bundle.zig`'ов doc-comment вверху файла — осознанное решение,
  bytecode/fn-ptr не сериализуется).
- `resolveForeignFunction` (`zig/core/resolver.zig:926`) — та же
  функция работает и для обычного `panos <file>`, и (без изменений) при
  перекомпиляции внутри fat binary. Для bare name (не `libc`/`хост`) она
  зовёт `foreignLibraryFilename`→`resolveForeignLibraryPath`, которая
  для bare name возвращает ГОЛОЕ имя файла (`"raylib.so"`, без
  директории) — и именно ЭТО голое имя уходит в `std.DynLib.open`/
  `dlopen`, то есть поиск делает OS loader, не panos. Здесь и живёт
  рантайм-зависимость, которую нужно убрать.
- `libc`/`хост` — отдельная ветка (строка 940), использует
  `dlopen(NULL, ...)` (символы уже загруженного образа процесса),
  никогда не открывает отдельный файл — **эту ветку трогать не нужно**,
  для неё "упаковывать нечего" в буквальном смысле (это не
  внешняя зависимость, это сам процесс).

## Залоченные решения (можно начинать без дополнительных вопросов)

1. **`libc`/`хост` остаются исключением**, как и сейчас — не bare-name
   библиотека в обычном смысле, upstream-поведение не трогать.
2. **Дедупликация по логическому имени** — если несколько модулей
   объявляют `внешний "raylib"`, упаковать байты один раз (та же логика
   уже есть для path-style, строки 128-138 `bundle.zig` — переиспользовать
   тот же паттерн, ключ на этот раз не путь, а логическое имя).
3. **Сборка и целевой запуск на одной архитектуре/ОС** — уже
   подразумеваемое ограничение всей fat-binary фичи (бинарник не
   кросс-компилируется, перекомпилирует panos-исходники при каждом
   старте на том же тулчейне). Упаковка bare-name библиотек НАЙДЕННЫХ на
   машине сборки следует этому же допущению, не вводит новое.
4. **Формат bundle (`bundle_magic`/`format_version`) может измениться**
   — новый тип записи или новое поле в `Entry`, `format_version`
   инкрементировать (сейчас `1`), старые bundle с этим агентом не
   встретятся (фича experimental, нет внешних потребителей формата).

## Открытые развилки — подтвердить перед стартом

### Развилка 1: как на этапе СБОРКИ найти реальный файл bare-name библиотеки

`resolveForeignLibraryPath` для bare name сегодня ничего не резолвит в
реальный путь — просто добавляет суффикс (`.so`/`.dylib`/`.dll`) и
отдаёт голое имя OS loader'у. Чтобы упаковать байты, нужно на этапе
`bundle.collect()` узнать, ГДЕ именно OS loader НАШЁЛ БЫ этот файл на
машине сборки. Два реалистичных варианта:

- **(a) Переиспользовать существующий dlopen-путь.** `collect()` уже
  бежит ПОСЛЕ обычного resolve-прохода (типа `resolveForeignFunction`
  уже вызывался и УСПЕШНО открыл библиотеку — иначе сборка бы упала с
  диагностикой раньше). Значит можно либо (i) сохранить handle из ЭТОГО
  прохода и переиспользовать его в `collect()`, либо (ii) в `collect()`
  самостоятельно вызвать `dlopen`/`LoadLibraryW` ещё раз тем же именем
  (дёшево — OS кеширует уже загруженный образ). После получения handle:
  - POSIX (Linux/macOS): `dladdr(fn_ptr, &info)` на УЖЕ разрешённом
    указателе символа (он у нас есть — `resolveForeignFunction` делает
    `dlsym` на `foreign.name`) → `info.dli_fname` — реальный путь файла,
    из которого загружен символ. `dladdr` есть в `<dlfcn.h>` на Linux
    (glibc/musl) и macOS — не строго POSIX, но фактически везде, где
    есть `dlopen` в этом кодовой базе уже используется через
    `std.c.dlopen`/`std.c.dlsym`, `dladdr` — соседняя функция того же
    заголовка, тот же уровень переносимости.
  - Windows: `GetModuleFileNameW(handle, buffer, len)` на HMODULE,
    полученном от `LoadLibraryW` — прямой аналог, уже есть прецедент
    ручных `extern "kernel32"` объявлений в `resolver.zig` (строка
    1048) для `LoadLibraryW`/`GetProcAddress` — добавить туда же.
- **(b) Отдельный, не-dlopen-based поиск** (парсинг `ld.so.cache`,
  перебор `LD_LIBRARY_PATH`/стандартных директорий вручную) — НЕ
  рекомендуется: дублирует логику, которую OS loader и так уже
  корректно делает, риск разойтись с реальным поведением `dlopen`.

**Рекомендация**: (a), через `dladdr`/`GetModuleFileNameW` на handle,
уже открытый существующим resolve-проходом (не заводить новый).
Нужно решить: `resolveForeignFunction` уже открывает handle ради
`dlsym` — стоит ли он **закрывать** его (`dlclose`) сразу после
получения `fn_ptr` (сегодняшнее поведение — не проверено явно,
предположительно keep-open, раз `fn_ptr` должен быть валиден всё время
жизни процесса) — если keep-open, `collect()` может переиспользовать
УЖЕ загруженный образ через повторный `dlopen` того же имени (ОС не
грузит второй раз, просто увеличивает refcount и возвращает тот же
handle) без нового рефакторинга сигнатур. Подтвердить это перед тем как
писать код — если утечка handle'ов уже осознанная (скорее всего да, раз
`fn_ptr` живёт весь процесс), это не новая проблема, просто факт, на
который можно опереться.

### Развилка 2: как на РАНТАЙМЕ fat binary заставить `внешний "raylib"` открыть ИМЕННО распакованный файл, а не искать через OS

Сегодня `resolveForeignFunction`/`resolveForeignLibraryPath` не имеют
понятия "у меня есть готовый абсолютный путь для этого логического
имени, не ищи через OS". Нужен новый inject-путь. Варианты:

- **(a) Override-таблица на уровне `Resolver`**, параллельно
  существующему `source_path`/`target_profile` полям (`zig/core/
  resolver.zig:304-320`) — новое поле, например
  `library_path_overrides: ?*const std.StringHashMap([]const u8)`,
  проверяется В НАЧАЛЕ bare-name ветки `resolveForeignFunction`: если
  `foreign.library` (без учёта suffix) есть в таблице — использовать
  готовый путь вместо `foreignLibraryFilename`, ОСТАЛЬНАЯ логика
  (dlopen/dlsym или LoadLibraryW/GetProcAddress) не меняется, просто
  меняется ЧТО передаётся как filename. Симметрично для path-style
  ветки менять не нужно — она уже самодостаточна (виртуальный
  temp-rooted `source_path` уже даёт правильный итоговый путь, см.
  текущий рабочий механизм для path-style в fat binary).
- **(b) Переписывать САМ `внешний`-decl** (AST/resolution уровень) —
  подменять `foreign.library` на абсолютный путь ДО того, как резолвер
  его увидит — отвергнуто: `foreign.library` приходит из `.pns`-текста,
  который отдаётся `BundleReader`'ом из ЧИТАЕМОГО ТОЛЬКО НА ЧТЕНИЕ
  bundle — переписывать AST постфактум ломает инвариант "код бандла ==
  код что был на сборке", усложняет debug/дифф.

**Рекомендация**: (a). Пробрасывать `library_path_overrides` нужно
через весь путь `zig/cli/main.zig:runFatBinary` → `panos_embed.Runtime`
(`zig/embed.zig`, `Runtime.init`'s options struct, соседнее с
`global_search_roots`/`program_args`/`foreign_profile_enabled`) →
`Resolver`. Проверить сигнатуры `Runtime.load`/внутренний
`resolveModuleForTarget`-подобный путь, где сегодня `target_profile`
уже прокидывается похожим образом — сделать по аналогии, не изобретать
новый механизм прокидывания.

### Развилка 3: библиотеки, которые НЕЛЬЗЯ безопасно упаковывать (драйвер/железо-специфичные)

Реальный риск, не гипотетический: `raylib` (мотивирующий пример из
`feedback_panos_pain_points_codex_report`) на Linux динамически тянет
`libGL.so`/системный OpenGL — ЭТО специфично для GPU-драйвера машины
СБОРКИ, копия, упакованная в бинарник, может НЕ РАБОТАТЬ или работать
неправильно на машине запуска с другим драйвером/видеокартой (в отличие
от "чистых" библиотек типа `libsqlite3`/`libcurl`, которые переносимы).
Аналогично `libX11`/`libwayland`/Vulkan ICD-loader'ы.

Слепая упаковка ВСЕГО bare-name дерева зависимостей (транзитивно, если
раскрывать через `dladdr` только ПРЯМО объявленные `внешний`-имена —
хорошо, транзитивные .so-зависимости самой raylib.so НЕ упаковываются
этим планом, только то, что явно названо в `внешний "..."`
декларациях panos-кода — это уже сужает риск, но raylib САМА может быть
объявлена как `внешний "raylib"`, и raylib — не проблема; проблема
только если кто-то явно напишет `внешний "GL"`/`внешний "X11"`).

**Нужно решить** (пользовательское/архитектурное решение, не техническое):
- (a) Упаковывать вообще всё bare-name без исключений, положиться на то,
  что пользователь сам не будет объявлять `внешний "GL"` напрямую (он
  и так вряд ли будет — обычно это транзитивная зависимость через
  raylib, которая НЕ отражена как явный `внешний` в panos-коде и потому
  само по себе не встретится в этом плане).
- (b) Завести allowlist/blocklist известных системных/драйверных имён
  (`GL`, `X11`, `Xrandr`, `Xi`, `vulkan`, `d3d*`, `opengl32` и т.п.),
  которые по умолчанию НЕ упаковываются, с явным флагом
  `panos build --compile --embed-all-libraries` для переопределения.
- (c) Ничего не решать заранее — упаковывать всё, но ДОБАВИТЬ явный
  warning в вывод сборки: "библиотека 'X' упакована с машины сборки —
  может не работать на машинах с другим GPU/драйвером, если это
  графическая/системная библиотека" (эвристика по имени не нужна,
  просто общее предупреждение при КАЖДОЙ bare-name упаковке).

**Рекомендация**: (c) для первой версии — простое общее предупреждение
дешевле, чем поддерживать allowlist, который придётся обновлять. (b) —
хорошее будущее развитие, не блокирует v1.

## Реализация (по шагам, после решения развилок 1-3)

1. **`zig/core/resolver.zig`**:
   - Новая функция уровня `resolveForeignLibraryPath`-сестра, например
     `locateBareLibraryFile(allocator, logical_name) !?[]const u8` —
     инкапсулирует Развилку 1 (dlopen-and-dladdr / LoadLibraryW+
     GetModuleFileNameW). Возвращает `null`, если библиотека не найдена
     (сборка должна тогда упасть с понятной ошибкой — см. п.3 ниже, не
     тихо пропускать, в отличие от сегодняшнего `bundle.zig:112`).
   - `Resolver` получает новое опциональное поле (Развилка 2а),
     `resolveForeignFunction`'s bare-name (не `libc`/`хост`) ветка
     проверяет его первым, до `foreignLibraryFilename`.

2. **`zig/core/bundle.zig`** `collect()`:
   - После текущего `else => continue` для bare names — заменить на
     вызов `locateBareLibraryFile`, если найден путь — читать байты
     (та же `readFileAlloc`+дедуп логика, что уже есть для path-style,
     строки 116-143), класть в `entries` под НОВЫМ ключевым
     пространством, например `"libs/<имя>.<суффикс>"` (не
     path-relative — у bare name нет "относительно чего", в отличие от
     path-style). Если `locateBareLibraryFile` вернул `null` — это
     реальная build-time ошибка (см. п.3), не тихий skip.
   - Рассмотреть: нужен ли новый флаг в `Entry` (`is_bare_library: bool`)
     отдельно от `is_library`, чтобы рантайм знал — заполнять
     `library_path_overrides` ТОЛЬКО для bare-упакованных записей
     (path-style продолжает работать через существующий
     source_path-relative механизм, ничего менять не надо).

3. **Build-time error handling** (`zig/cli/main.zig`, где сегодня
   вызывается `bundle.collect` внутри `--compile`-ветки `runBuild`):
   если `locateBareLibraryFile` не нашла библиотеку на машине сборки —
   явная диагностика ("panos build --compile: библиотека 'X' не
   найдена на машине сборки, установите её перед сборкой fat binary"),
   не молчаливый пропуск (текущее поведение для bare name — тихий skip
   — было ОК, пока bare name вообще не упаковывался; теперь, раз цель
   "полностью упаковать", отсутствие библиотеки на сборочной машине
   должно быть build-time ошибкой, а не рантайм-сюрпризом на целевой).

4. **`zig/cli/main.zig`** `runFatBinary`:
   - При распаковке `is_library` записей — для записей из нового
     `"libs/"`-пространства СТРОИТЬ `library_path_overrides` map
     (логическое имя → абсолютный извлечённый путь) вместо/в дополнение
     к текущему голому "пишем на диск и всё" (path-style записи
     продолжают писаться как раньше — их override не нужен, source_path
     механизм уже работает).
   - Прокинуть `library_path_overrides` в `panos_embed.Runtime.init`
     options (Развилка 2, п. "пробрасывать через Runtime").

5. **`zig/embed.zig`** — расширить `Runtime.init`'s options struct
   новым полем, прокинуть до места, где сегодня строится/используется
   `Resolver` (там же, где `target_profile`/`source_path` уже
   устанавливаются per-module).

## Верификация

- Новый fixture: panos-программа с `внешний "sqlite3"` (bare name,
  реальная библиотека, которая почти наверняка ЕСТЬ на CI-машинах —
  безопаснее для теста, чем raylib с его GPU-специфичностью) —
  `panos build --compile`, скопировать/запустить получившийся бинарник
  в ОКРУЖЕНИИ БЕЗ `sqlite3` на стандартных путях (например, `env -i
  PATH=/usr/bin ...` с намеренно урезанным `LD_LIBRARY_PATH`/без
  `brew`-путей на macOS) — подтвердить, что бинарник всё равно находит
  и вызывает библиотеку (упакованную копию), не падает на "библиотека
  не найдена".
- Регрессия: существующие path-style fat-binary тесты (если есть в
  `tests/`) должны остаться зелёными без изменений — path-style
  механизм в этом плане не трогается.
- Дедупликация: fixture с ДВУМЯ модулями, оба объявляют `внешний
  "sqlite3"` — bundle должен содержать ОДНУ копию байт библиотеки, не
  две (проверить размер bundle / список entries программно, не только
  "работает").
- Ошибка при отсутствии библиотеки на машине сборки: fixture с заведомо
  несуществующим `внешний "определённо_нет_такой_библиотеки_12345"` —
  `panos build --compile` должен упасть с понятной диагностикой ДО
  генерации бинарника, не молча пропустить (текущее поведение) и не
  крашнуться с невнятной ошибкой.

## Вне рамок этого плана (сознательно)

- Кросс-компиляция fat binary (сборка на одной ОС/архитектуре, запуск
  на другой) — не поддерживается сегодня в принципе (весь пайплайн
  перекомпилируется на целевой машине тем же тулчейном), этот план не
  меняет этого ограничения.
- Транзитивные зависимости упакованных библиотек (упаковываем только то,
  что явно названо `внешний "..."` в panos-коде, не то, что ЭТА
  библиотека сама динамически линкует) — см. Развилка 3.
- Allowlist/blocklist системных библиотек (Развилка 3, вариант b) —
  явно отложено на будущее, если понадобится после реального
  использования.

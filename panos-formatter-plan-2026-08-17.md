# План: `panos fmt` — форматтер кода

Снапшот 2026-08-17. Не начато — план для реализации/передачи. 6
архитектурных развилок обсуждены и решены (ниже, "Залоченные решения"),
остальное — конкретная последовательность работы.

## Контекст, откуда взялись развилки

Найдено при разборе: лексер (`zig/core/lexer.zig`, `skipWhitespaceAndComments`)
съедает обычные `//`-комментарии целиком — ни токена, ни span'а не
остаётся. Спасаются только contiguous `///` (уходят в `token.doc`, тема
отдельного LSP-hover плана). Значит наивный AST-reprint (parse → печатать
канонично с нуля) молча удалит каждый `//`-комментарий в файле —
неприемлемо для v1.

## Залоченные решения

1. **Zero-config.** Без опций стиля вообще (gofmt-модель, не
   rustfmt-модель) — один канонiчный вывод, никаких holy wars, ничего
   не поддерживать/документировать по конфигу.
2. **Синтаксический, не semantic-aware.** Форматтер требует только
   успешный ПАРСЕР (`parser.zig`), не typecheck. Обязательное следствие:
   должен уметь форматировать файл, который не типизируется (временная
   ошибка посреди редактирования) — иначе format-on-save ломается
   ровно тогда, когда нужнее всего.
3. **Ширина строки — раны/codepoints, не байты.** Кодовая база
   кириллица-heavy, UTF-8 (2 байта/символ) — байтовый подсчёт ширины
   переносил бы строки вдвое агрессивнее на кириллице, чем на латинице.
   Тот же класс бага, что уже задокументирован в hardening-плане
   (рановый vs байтовый индекс в `строки.*`) — использовать rune-count
   (аналог `строки.длина`, не `длина_байт`) для решения "перенести
   строку или нет".
4. **Каноничная форма `выбор`-arm — вывод определяется числом
   statement'ов, не тем, как написал пользователь.** Ровно 1 statement
   в теле arm'а → всегда печатать короткую форму `Шаблон -> выражение`.
   2+ statement'ов → всегда `Шаблон тогда ... конец`. Не настройка, не
   "оставить как есть" — детерминированное правило, применяется
   одинаково при любом входе.
5. **CLI первым, LSP — сразу следом, тот же движок.** `panos fmt` —
   отдельная команда (`zig/cli/main.zig`, тот же dispatch-паттерн, что
   уже есть у `build`, строка ~447: `if (std.mem.eql(u8, file_path,
   "build"))`). `--check` режим — точный прецедент внутри же экосистемы
   (`codegen --check`, см. CLAUDE.md "Recent Changes" — сравнивает что
   БЫЛО БЫ сгенерировано с тем, что на диске, exit non-zero на
   расхождении, ничего не пишет). LSP `textDocument/formatting` —
   отдельный, более поздний шаг, вызывает тот же форматирующий движок
   как библиотеку.
6. **Добавлять trailing comma** на многострочных списках (Rust/gofmt-
   конвенция, снижает diff-шум при будущих правках). Важно: panos
   исторически имел реальные баги именно вокруг trailing comma
   (`005-language-fixes` — несколько небезопасных call-sites чинили) —
   при реализации перепроверить, что ВСЕ позиции, куда форматтер
   добавляет запятую, парсер сегодня действительно безопасно принимает
   (call args/enum variant types/pattern-constructor args/generic
   type-args/tuple-type elements — список мест, где это когда-то было
   небезопасно, из той же памяти).

## Архитектура

**Token-stream/concrete-syntax подход**, не AST-reprint — прямое
следствие решения о комментариях (см. "Контекст" выше). Форматтер
работает на паре (список токенов от `lexer.tokenize`, сырой исходный
текст) — для каждой пары соседних токенов решает: сколько пробелов/
переносов строк поставить между ними (по правилам индентации/стиля),
КОПИРУЯ дословно любой текст зазора между токенами, который является
комментарием (обнаруживается сканированием сырого текста между
`token[i].span.end` и `token[i+1].span.start` на `//`-префикс — тот же
приём, каким лексер сам находит комментарии, просто не отбрасывая
найденное). AST нужен ТОЛЬКО для структурных решений, требующих знания
грамматики (где заканчивается один statement/начинается следующий при
schlopывании match-arm формы — п.4 выше; где вставлять trailing comma
— п.6) — не для самого текстового вывода.

**Обязательное свойство корректности** (проверять тестами, не
предполагать): вывод форматтера, поданный обратно на вход
`parser.parse`, должен давать АСТ, структурно эквивалентный исходному
(с точностью до spans/doc-attachment) — форматтер физически не должен
иметь возможность изменить смысл программы. Плюс идемпотентность:
`format(format(x)) == format(x)` побайтово — стандартное свойство
любого форматтера, тестируется property-тестом на существующем
`tests/conformance/` корпусе + фикстурах `std/`/`demo/`.

## Фазы реализации

1. **MVP: нормализация отступов/пробелов, без переноса строк.**
   Token-stream проход, канонiчный indent (решить ширину — табы или N
   пробелов, тоже часть zero-config решения, не отложено на
   пользователя) на основе вложенности блоков (`если`/`для`/`пока`/
   `функ`/`тип`/`выбор`/`конец` — глубина считается по structural
   AST-обходу, не эвристикой по токенам). Комментарии копируются как
   есть, никакого line-wrapping ещё нет.
2. **Line-wrapping для длинных строк** (правило #3 — рановый подсчёт
   ширины). Разбивка длинных списков параметров/аргументов на несколько
   строк по тому же canonical стилю, что уже нужен для п.6 (trailing
   comma на многострочных списках — эти два пункта естественно идут
   вместе, один и тот же code path "список стал многострочным").
3. **Каноничная форма match-arm** (правило #4) — отдельный проход,
   требует знания числа statement'ов в теле arm'а (из AST), не только
   токенов.
4. **Trailing comma insertion** (правило #6), с перепроверкой
   парсер-safety по списку мест из `005-language-fixes`.
5. **`panos fmt [--check] [--write] <путь>`** (`zig/cli/main.zig`) —
   `--check`: exit non-zero + список файлов с расхождением, ничего не
   пишет (CI-режим, прямая аналогия `codegen --check`). Без флага или
   `--write`: перезаписывает на месте. Путь — файл или директория
   (рекурсивно, `.pns`).
6. **LSP `textDocument/formatting`/`textDocument/rangeFormatting`**
   (`zig/lsp/main.zig`, тот же dispatch-паттерн, что `hover`/
   `completion` уже используют) — вызывает движок из п.1-4 как
   библиотеку, оборачивает результат в LSP `TextEdit[]`.

## Верификация

- Property-тесты (идемпотентность + AST-эквивалентность выхода) —
  прогнать на ВСЕХ `.pns`-файлах в `std/`, `demo/`, `tests/conformance/`
  как реальном корпусе, не только на синтетических фикстурах.
- Явный тест на сохранение комментариев: файл с `//`-комментарием в
  каждой синтаксически значимой позиции (перед декларацией, внутри
  блока, в конце строки после кода, между элементами многострочного
  списка) — после форматирования комментарий на месте, дословно.
- CI: `panos fmt --check` на весь репозиторий (`std/`, `demo/`,
  `panosiki/*` если применимо) — либо сразу зелёный (репо уже
  консистентно), либо явный, отдельный "привести в соответствие"
  коммит перед тем, как гейтить CI на этом.

## Вне рамок этого плана

- Настраиваемость стиля (zero-config решение, п.1) — никогда не
  становится частью API, разве что отдельным будущим решением с новым
  обсуждением.
- Semantic-aware форматирование (например, канонический порядок
  named-аргументов по объявлению структуры — упоминалось при
  обсуждении metamorphic-тестирования как потенциальная фича) — прямое
  следствие решения п.2 (только синтаксис), сознательно исключено.

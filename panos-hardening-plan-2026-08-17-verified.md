## Реально ОТКРЫТО (перепроверено, актуально на 2026-08-17)

### WASM AOT closures — 2 оставшихся пункта
1. **Процесс (актор)-захваты** — `classifyCaptureDepth`'s `.process =>
   .unsupported`, явная диагностика уже есть (`18ead4b`, "AOT handle
   указывает на actor frame в сбрасываемой арене, а Phase 1 scheduler не
   сохраняет актор между DOM-вызовами") — ЭТО архитектурное ограничение
   Phase 1 scheduler'а, не забытый баг. Реальный фикс требует, чтобы
   актор переживал между DOM-событиями (сам scheduler дизайн, крупная
   задача) — не "one-sitting".
2. **Вложенный generic-параметр внутри захватываемого поля** —
   `concreteCaptureFieldType`'s собственный комментарий: "Nested generic
   expressions are deliberately rejected until lowering can substitute
   them recursively as well" — сегодня резолвится только ОДИН уровень
   generic-плейсхолдера (прямое поле), не рекурсивно (поле generic-типа,
   чьё СВОЁ поле тоже generic). Узкий, явно задокументированный remaining
   gap.

Плюс из старого списка, НЕ переисследовано в этом проходе (нужно ли
исправлять — открытый вопрос):
- DOM closure selector eval order — код изменился настолько (унификация

## Обновлённый порядок работы

Поскольку почти все "дешёвые" и "узкие" пункты из предыдущей версии
плана уже закрыты сами собой, реальный remaining scope for a hardening
period куда меньше, чем казалось на 2026-08-15:

### Phase A — реально осталось сделать (в порядке дешевизны)
1. **`panos_embed` §1** (диагностики) — перенос `formatDiagnostic` из
   `cli/main.zig` в `panos_core`, см. полный план в
   `panos-embed-api-followup-plan-2026-08-17.md`.
2. **`panos_embed` §4** (тесты error-путей) — дёшево, независимо от
   пункта выше.
3. **Nested generic capture** (closures, пункт 2 выше) — узкий, но
   реальная работа над `concreteCaptureFieldType`, не "one-sitting"
   (рекурсия по вложенным generic-полям).
4. **Doc-комментарии (`///`) не доходят до LSP hover** — найдено
   2026-08-17: лексер реально собирает contiguous `///`-строки в
   `token.doc` (`lexer.zig`, тест `"lexer attaches only contiguous doc
   comments"`), парсер кладёт их в AST-декларации (`ast.zig:341-413`,
   поле `doc` на нескольких decl-вариантах) — но ДАЛЬШЕ ничего их не
   читает. `grep` по `zig/core/*.zig`+`zig/lsp/*.zig` не находит ни
   одного потребителя за пределами lexer/parser. `zig/lsp/main.zig:195`
   (`hover`) формирует ответ ТОЛЬКО из `expressionTypeName` (имя типа),
   doc-строка никак не участвует. Распарсенные, но мёртвые данные — не
   ошибка, просто недоделанная фича (не проверялось, было ли иначе в
   Odin-версии — исходники удалены, сравнить не с чем).

   План:
   - Нужна обратная связь `SymbolId → DeclId` (сегодня есть только
     прямая `Resolution.decl_symbols: DeclId → SymbolId`,
     `resolver.zig:175`) — самый дешёвый вариант: построить временную
     `AutoHashMap(SymbolId, DeclId)` на месте в `hover()` инвертированием
     `decl_symbols` (одна файловая LSP-сессия за раз, decl'ов немного,
     O(n) построение на каждый hover — приемлемо, не нужен постоянный
     индекс).
   - `runner.SourceAnalysis` — новый метод, симметричный
     `expressionTypeName` (`runner.zig:96`), например
     `expressionDoc(self, expression: ast.ExprId) ?[]const u8`: через
     `resolution().expr_symbols.get(expression)` получить `SymbolId`,
     через новую обратную карту — `DeclId`, через `tree.decl(decl_id)`
     — сам decl-узел, из него достать поле `.doc` (нужен `switch` по
     варианту декларации — `.doc` есть не у всех, см. `ast.zig:341-413`,
     аккуратно обработать варианты без него).
   - `zig/lsp/main.zig:195` (`hover`) — после получения `type_name`,
     дополнительно дёрнуть `expressionDoc`, если есть — включить в
     `writeHoverResponse` (сегодня принимает только `type_name`+`range`,
     нужно расширить сигнатуру/формат MarkupContent, LSP hover уже
     поддерживает markdown-контент по протоколу).
   - Тест: `zig/lsp/main.zig`'s существующий hover-тест
     (строка ~1713, `"textDocument/hover"` JSON-RPC) — расширить фикстурой
     с `///`-комментарием перед функцией, проверить что doc-текст
     реально попадает в ответ, не только тип.
   - Опционально, отдельным шагом (не блокирует основной): completion
     (`zig/lsp/main.zig:236`) тоже мог бы показывать doc как
     `documentation`-поле `CompletionItem` — тот же источник данных,
     тот же lookup-механизм, чисто аддитивно после hover сделан.

### Phase B — верификационный проход (что НЕ трогали, но стоит подтвердить)
1. `zig build conformance` + `integration` + `bench` — прогнать,
   зафиксировать baseline (сегодня неизвестен).
2. `ISSUES.md`'s 9 пунктов — построчно сверить с текущим `zig/core/`,
   не доверять файлу на слово (он сам иногда прав, иногда просто
   старая пометка) — то же правило, что уже применили выше к
   докс-багам (не гадать, реально проверить).
3. Stdout-capture / Windows CI flake'и — перепрогнать, зафиксировать
   актуальную частоту.
4. **CI cron на continuous fuzzing.** Найдено 2026-08-17: `zig build
   fuzz` — реальный crash-oracle fuzzing (`std.testing.fuzz`,
   3 цели — `lexer.zig`/`parser.zig`/`runner.zig`'s "never panics"
   тесты, последняя покрывает ВЕСЬ пайплайн lex→parse→resolve→
   typecheck→compile→run, seed-корпус — осмысленные near-miss формы,
   не случайные байты). Инфраструктура готова, но `grep` по
   `.github/workflows/` не находит НИ ОДНОГО файла, упоминающего
   "fuzz" — continuous coverage-guided режим (`zig build fuzz --fuzz`)
   никогда не запускался дольше одного прохода seed-корпуса
   (то, что бесплатно попадает в обычный `zig build test`). Дёшево
   добавить: новый `.github/workflows/fuzz.yml`, cron (например
   ежедневно ночью) или `workflow_dispatch`, N минут `zig build fuzz
   --fuzz` на каждую из 3 целей, crash → artifact с репродуцирующим
   входом + fail build. Чисто конфигурационная работа, ноль изменений
   в коде.

### Phase C — архитектурно крупное (заморожено, без изменений с прошлой версии плана)
- Актор-scheduler переживание между DOM-событиями (нужно для closures
  пункт 1 выше) — реальная архитектурная работа, отдельный research/
  plan-mode проход.
- `panos_embed` §2 (reset/reload), §3 (sandboxing) — фичи, не hardening.
- Fat binary bare-name library bundling — отложено пользователем.
- Codegen/метапрограммирование — отдельная незавершённая тема.
- pan build-hooks — требует security-дизайна (pnpm/Deno allowlist-модель).
- **Metamorphic-тестирование typechecker'а.** Найдено 2026-08-17,
  триггер — обсуждение того, почему `zig build fuzz` (crash-oracle,
  см. Phase B п.4) не поймал ни один из реально найденных этой сессией
  багов: crash-oracle фаззинг проверяет только "не упало", а весь
  класс багов, что чинили (ложный дубликат-вариант, `Сравниваемое` вне
  generic, `получить_сигнал` неверный тип и т.д.) — тихо НЕПРАВИЛЬНЫЙ
  ответ, не крах. Нужен другой oracle: не "упало ли", а "два
  семантически эквивалентных варианта дают ОДИНАКОВЫЙ typecheck-
  результат". Unparser/pretty-printer в кодовой базе НЕТ (`grep` по
  `zig/core/*.zig`+`zig/lsp/*.zig` не находит AST→source рендер) —
  трансформации должны работать на уровне ИСХОДНОГО ТЕКСТА (простые
  текстовые операции: перестановка аргументов внутри `(...)`, границы
  top-level деклараций для reorder), не AST-мутация с реprint.

  Конкретные инвариантные пары для реализации (каждая — прямое
  обобщение реально найденного бага, не гипотеза):
  1. `пер x = expr` vs `пер x: T = expr` (T = реально выведенный тип)
     — идентичный дальнейший typecheck. Обобщает баг
     "`выбор получить()` напрямую падало, через `пер x: T` — работало".
  2. `Т(x = 1, y = 2)` vs `Т(y = 2, x = 1)` — идентичный результат.
     Уже есть КАК ПРИМЕР в fuzz seed-корпусе, но не как ПРОВЕРЯЕМЫЙ
     инвариант (фаззер сравнивает только "не упало", не сравнивает
     диагностики между парой).
  3. Перестановка двух независимых (не зависящих друг от друга по
     имени) top-level деклараций — идентичные диагностики. Ловит
     cross-pass order-desync.
  4. Метод через конкретный тип напрямую vs через interface-типизированную
     переменную с тем же значением — идентичный результат. Обобщает
     `interface_self_placeholders`-баг (Self-типизированный метод через
     interface-переменную не резолвился).
  5. Два arm'а с разными narrowing-паттернами для одного варианта
     `выбор` (не дубликат) vs два идентичных (реальный дубликат) —
     сгенерировать автоматически много форм паттернов вместо 2
     вручную написанных regression-тестов.

  Реализация: новый fuzz-таргет (`typechecker_metamorphic_test.zig`
  или добавка в `runner.zig`, тот же `std.testing.fuzz`-механизм, что
  Phase B п.4) — байты-мутатор решают, КАКУЮ трансформацию применить
  и К какому месту в seed-программе, оба варианта прогоняются через
  `runner.analyzeSource`, сравнивается число/severity диагностик.
  Дороже обычного crash-oracle (два прогона пайплайна + сравнение
  вместо одного "не упало"), реальная новая инфраструктура — отдельный
  research/plan-mode проход, не "one-sitting".
- **Distinct рановый/байтовый index-типы.** Найдено 2026-08-17 (заново
  подтверждено, старая находка `ISSUES.md` §6 жива): `строки.найти`
  (рановый индекс) и `строки.срез_байт`/`строки.длина_байт` (байтовый)
  оба типизированы голым `Целое` — ничего не мешает передать результат
  одного в другой, для не-ASCII текста это молча портит данные
  (реальный подтверждённый случай: "купить хлеб" → "купит�"). Сегодня
  единственная защита — предупреждение в доках
  (`docs/src/language/standard-library.md:308-309`), не type safety.
  Настоящий фикс — новые wrapper-типы (`РановыйИндекс`/`БайтовыйИндекс`
  или похожие), ломающая правка сигнатур ВСЕХ вызовов `строки.найти`/
  `строки.срез`/`строки.срез_байт` по `std/`, `panosiki/*`, фикстурам —
  требует отдельного research/plan-mode прохода (масштаб, обратная
  совместимость, точный набор affected call sites) прежде чем
  оценивать как "начать сейчас".
- **Явный generic-argument syntax `ф[Тип](...)`.** Не существует в
  парсере вообще (подтверждено `grep`, 2026-08-17) — единственный
  недостающий кусок из sound-core type-system плана
  (`project_panos_sound_core_typesystem_direction`, poison/unconstrained
  split уже сделан). Сегодня, если вывод типа не может определить `T`
  из контекста аргументов/return-типа, единственный исход —
  диагностика `"не удалось вывести type-параметр 'T'"`
  (`type_checker.zig:4585`/`4692`/`5232`) без способа явно указать `T`
  вручную — обходной путь только через промежуточную типизированную
  `пер`-привязку, если она вообще применима. Системно самый ценный
  пункт из всего списка (без него нельзя убрать последний permissive
  fallback "нет контекста — молча пропускаем" в typechecker'е, реальный
  код на это полагается), но и самый крупный — нужны изменения в
  парсере (новая синтаксическая позиция после имени вызываемого,
  учесть взаимодействие с уже существующим `x как Тип`-кастом и с
  quалифицированными вызовами `модуль.функция[Тип](...)`) и в
  typechecker'е (явные substitutions вместо только выведенных, решить
  что происходит при конфликте явного `T` с типом реально переданного
  аргумента — hard error или explicit overrides infer). Отдельный
  research/plan-mode проход, не "one-sitting".

# План: генератор SQL/data-mapper по типам структур

Снапшот 2026-08-17. Не начато — план для реализации/передачи. Родился
из обсуждения "полноценного ORM" — сознательно сужен до SQL-first +
тонкий codegen-ассист, не ORM-движок (обоснование ниже).

## Залоченное решение: SQL-first, не ORM

**Не строить**: identity map, dirty-checking/change-tracking,
lazy-loading relations, unit-of-work — то, что определяет ORM как
класс инструмента. Обоснование (из обсуждения):
1. Главная традиционная причина тянуться к ORM — SQL-injection safety
   — уже решена на уровне примитива `бд.*` (только позиционные `?`,
   string-concat SQL пути физически нет).
2. Портируемость между БД-движками (другая классическая причина ORM)
   не применима — `бд.*` только SQLite, абстракции над другими
   движками нет.
3. Полный ORM был бы первым по-настоящему "магическим" слоем в
   экосистеме, где всё остальное сознательно explicit (см. `бд.*`'s
   собственный дизайн — голые Строка-колонки, никакой рефлексии).
4. N+1/leaky-abstraction — реальная, документированная цена полных
   ORM индустриально, не гипотеза.

Итоговый класс инструмента — **типизированный data mapper**
(row↔struct маппинг через генерируемый код), тоньше и query builder'а,
и тем более ORM: без identity map, без dirty-tracking, без lazy
relations.

## Размещение

Расширяет существующий `../panosiki/codegen/` (тот же repo, что уже
генерирует `&Json` — новый обработчик в том же `Соответствие(Строка,
функ...)`-реестре), **не** `std/` — codegen-логика build-time
инструмент, ей не место рядом с рантайм-стандартной библиотекой (тот
же принцип, по которому сам `codegen` изначально не пошёл в
`std/кодирование/`). Дефолт — расширить СУЩЕСТВУЮЩИЙ репозиторий, не
заводить новый `panosiki/*` пакет, если не всплывёт причина разделять
(отдельная каденция релизов/зависимость, которую не хочется тянуть в
общий codegen) — не финально решено, пересмотреть при старте
реализации, если появится повод.

## Scope v1 (единственное, что начинать сейчас)

1. **DDL-генерация** — `&Таблица(...)`-аннотация на структуре →
   `CREATE TABLE` из полей. Тип-маппинг: `Строка` → `TEXT`, `Число`/
   `Целое` → `REAL`/`INTEGER` (решить точное соответствие при
   реализации), `Булево` → `INTEGER` (0/1), `Опция(T)` → nullable
   колонка (естественное соответствие — `бд.*` уже опускает NULL-поле
   из результирующего `Соответствие` вместо `""`, `.есть()`/
   `.получить()` тот же идиоматичный паттерн переиспользуется).
2. **CRUD codegen** — фиксированные, генерируемые ОДИН РАЗ на этапе
   кодогенерации функции: `Создать`/`Найти(по id)`/`Обновить`/
   `Удалить`. `INSERT`/`UPDATE` — позиционные `?` в порядке объявления
   полей структуры (соответствует существующему `бд.*` API, ничего
   нового в core не нужно). Чтение строки в структуру — генерируемый
   код сам конвертирует `Строка`-колонки в `Число`/`Целое`/`Булево` по
   полю (`строки.в_число` и т.п. — тот же объём работы, что и
   вручную писать, просто сгенерировано один раз).
3. **BLOB-поля** — генератор явно ОТКЛОНЯЕТ с диагностикой (нет
   безопасного маппинга, `бд.*` сам не поддерживает BLOB в
   `.запрос()`) — та же дисциплина, что `&Json`-генератор уже
   применяет к неподдержанным полям.
4. Аннотации переиспользуют существующий механизм именованных
   аргументов (`AnnotationArgument{name, value}`, `ast.zig:22-31`) —
   `&Таблица(имя: "задачи")` на структуре, `&ПервичныйКлюч` на поле —
   ничего нового в парсере/резолвере не требуется, только новый
   потребитель в codegen-driver'е.

## Scope v2 (отдельная волна, после v1 проверен на реальном использовании)

- **Отношения (foreign keys)** — реальная ORM-смежная фича, СОВПАДАЕТ
  со старым открытым пробелом (`feedback_panos_pain_points_codex_report`,
  "нет стабильных entity ID/referential integrity инфраструктуры") —
  решать здесь закрывает оба сразу, не отдельной задачей позже.
- **Транзакции** — тонкая обёртка `Соединение_БД.транзакция(функция) ->
  Результат`, реализуется через обычный SQL-текст (`BEGIN`/`COMMIT`/
  `ROLLBACK` — уже выполнимо через `.выполнить(...)`, проверено
  2026-08-17 — в `бд.*` нет специальной поддержки транзакций, и не
  нужна, это чистый library/generated-level код, без core-изменений).

## Scope v3 (отдельный research/plan-mode проход каждый, не решать заранее)

- **Query builder** (динамическая композиция `WHERE`/`ORDER BY` в
  рантайме) — реальная архитектурная развилка, НЕ решена: (а) остаётся
  build-time — генератор кодирует фиксированный набор запросов по
  аннотациям (`&Найти_по(поле)` → `WHERE поле = ?`), никакой динамики в
  рантайме, безопасно by construction автоматически; (б) настоящий
  runtime DSL (структуры-предикаты, компилируемые в SQL-текст
  динамически) — обязан остаться safe-by-construction (не превратиться
  в string-concat дыру, которую `бд.*` сознательно исключил) — сравним
  по объёму работы с самим генератором, отдельный проход.
- **Миграции** — versioned migration-файлы (руками написанные up/down
  SQL, Rails/Diesel-модель), НЕ автоматический schema-diff против живой
  БД (ненадёжно/опасно для прод-данных, зрелые ORM его избегают
  осознанно) — залочено как направление, реализация отдельно.

## Порядок работы

v1 → реальное использование (хотя бы один настоящий проект, не
синтетический пример) → по факту опыта решать, нужны ли v2/v3 вообще,
в каком порядке. Не начинать v2/v3 просто потому что "раз уж
делаем ORM" — обоснование каждой волны выше явно завязано на
конкретную, не гипотетическую причину.

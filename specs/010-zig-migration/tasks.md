- [x] T038 [US3] Implement scheduler, actors and data-only async completions in `zig/core/scheduler.zig`. — functionally complete inline in `vm.zig` (no standalone `scheduler.zig` file, matching every other native adapter in this migration). The original T027 actor model was recursive-run-to-completion (`отправить()` synchronously ran the target process on the Zig call stack, `получить()` faulted on an empty mailbox instead of waiting) — replaced with a real round-robin coroutine scheduler: `Process` (`value.zig`) now holds its OWN persistent `frames`/`stack`, `runScheduler`/`runProcessSlice` (`vm.zig`) swap them into the shared `Vm.stack`/`Vm.frames` per scheduling slice (same swap discipline as Odin's `run_scheduler`), and `получить`/`получить_сигнал`/`await_async` genuinely suspend (`StepOutcome.suspended`, `frame.ip` rolled back so the same instruction re-dispatches next chance) instead of faulting. Non-blocking actor I/O (the "data-only async completions" half): a hand-rolled `AsyncQueue` (mutex+condition via `std.Io.Mutex`/`std.Io.Condition` — Zig 0.16 moved these off `std.Thread` onto `std.Io`, no raw OS mutex exists without an `Io` handle) backed by `std.Thread.spawn`-per-job workers, ALL allocating on `std.heap.page_allocator` (never `Vm.allocator`, which may not be thread-safe — same motivation as Odin's `vm_heap_allocator()`). Every previously-synchronous I/O builtin now goes through submit+`await_async`: `фс.прочитать/записать`, `Файл.прочитать/прочитать_строку/записать`, `сеть.подключиться`, `Соединение.получить/получить_строку/отправить`, `сеть.http_запрос`, `бд.открыть/выполнить/запрос`. `gc_pin`/`gc_unpin` (`Heap.pinned`, `gc.zig`) added for the streaming-handle cases (`Connection`/`FileHandle`/`SqlConnection` hold an `in_flight` flag too, gating a concurrent second op on the same handle — `Listener` deliberately has NEITHER, since concurrent `.принять_запрос()` calls are the point of a server, not a race). Verified live and via automated tests (`runner.zig`) that an independent process genuinely completes while another awaits real file/TCP/HTTP/SQLite I/O — not just "eventually correct", actually non-blocking. See progress-report.md ("Планировщик процессов", "Неблокирующий I/O" sections) for full design history including the BEAM-VM-inspired discussion that led here (rejected a literal Odin `core:thread.Pool` port in favor of this shape, then converged on the same worker-pool idea since Zig 0.16 has no epoll/kqueue-backed `Io` implementation to build a true single-thread reactor on).

## Dependencies and execution order

- Phase 1 blocks every implementation phase; T001–T009 establish the
  executable compatibility baseline.
- Phase 2 blocks US1–US3 because they all need spans, diagnostics and target
  policy.
- US1 (Phase 3) supplies the semantic/runtime core needed by US2 and US3.
- US2 extends that core with module and stdlib semantics.
- US3 depends on US1/US2 for all delivered targets; T039–T041 can proceed in
  parallel after T038’s adapter protocol is stable.
- US4 documentation/CI becomes authoritative only after US3 builds, but its
  source documentation can be drafted in parallel.
- Phase 7 is the only phase that changes existing release paths.

## Parallel opportunities

- T003–T006 are independent after T001/T002.
- T011–T014 can be developed in parallel after the public package root exists.
- T017 and T019 are separate lexer/AST files; T039–T041 are separate native
  adapter files; T054–T056 are independent cutover validations.
- Parallel work must not define incompatible `Span`, `Value`, `Type_Id` or
  `Target_Profile` models; those are owned by T011–T013 and T023/T027.

## Implementation strategy

1. **MVP**: complete Phase 1 and a tiny Phase 2/US1 vertical slice — source →
   lexer → parser → diagnostics in a Zig CLI — before porting typechecker or
   VM.
2. **Expand by conformance tier**: promote parser, semantic and runtime cases
   only after their previous tier is green.
3. **Keep external boundaries last**: native services, AOT WASM and LSP attach
   to a proven core rather than driving its design.
4. **Cut over once**: no production hybrid; Odin is a reference-only oracle
   until Phase 7.

# Feature Specification: Sound Type Checking

**Feature Branch**: `011-fix-type-soundness`  
**Created**: 2026-08-10  
**Status**: Draft  
**Input**: User description: "Исправить слабые места тайпчекера: безопасную присваиваемость функций, допустимость целей присваивания, именованные аргументы и несколько интерфейсных ограничений generic-параметра. Для нескольких ограничений сохранить все необходимые возможности интерфейсов в runtime-значении."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Безопасные функции и присваивания (Priority: P1)

Разработчик получает диагностическое сообщение до запуска, когда передаёт функцию с более узким типом параметра туда, где возможен вызов с более широким типом, или пытается записать значение в недопустимую цель.

**Why this priority**: Эти случаи сейчас могут пройти проверку и завершиться ошибкой выполнения либо нарушить обещания типов.

**Independent Test**: Компиляция программ с несовместимой функцией или записью в строку завершается Type Error; корректные записи в массив и соответствие по-прежнему выполняются.

**Acceptance Scenarios**:

1. **Given** функция, принимающая конкретный реализующий тип, **When** её передают вместо функции, принимающей интерфейс, **Then** программа получает диагностическое сообщение и не запускается.
2. **Given** строковое значение, **When** программа присваивает значение по его индексу, **Then** программа получает диагностическое сообщение и не доходит до runtime error.
3. **Given** массив или соответствие, **When** программа присваивает значение по допустимому индексу или ключу, **Then** присваивание остаётся корректным.

### User Story 2 - Полные возможности нескольких интерфейсных ограничений (Priority: P1)

Разработчик может объявить generic-параметр с несколькими интерфейсными ограничениями и безопасно вызвать методы любого из этих интерфейсов внутри generic-функции.

**Why this priority**: Синтаксис уже принимает несколько ограничений, но значение должно сохранять все заявленные возможности, а не только одну из них.

**Independent Test**: Программа с `T: A + B`, вызывающая метод `A` и метод `B`, компилируется и возвращает ожидаемый результат для типа, реализующего оба интерфейса.

**Acceptance Scenarios**:

1. **Given** тип, реализующий интерфейсы `A` и `B`, **When** его передают в generic-функцию с ограничением `T: A + B`, **Then** вызовы методов обоих интерфейсов успешно выполняются.
2. **Given** тип, реализующий только один из обязательных интерфейсов, **When** его передают в такую функцию, **Then** программа получает диагностическое сообщение о невыполненном ограничении.
3. **Given** generic-функция с несколькими ограничениями и вложенными вызовами, **When** значение передаётся дальше в совместимую generic-функцию, **Then** все требуемые интерфейсные возможности сохраняются.

### User Story 3 - Предсказуемые именованные аргументы (Priority: P2)

Разработчик может вызывать методы с именованными аргументами в любом порядке; для конструкторов вариантов перечислений язык либо выполняет именование корректно, либо отклоняет его на этапе type checking понятной диагностикой.

**Why this priority**: Документация обещает именованные аргументы методов, но ошибка сейчас появляется позднее и в другой фазе.

**Independent Test**: Вызов метода с переставленными именованными аргументами создаёт тот же результат, что и позиционный вызов; неподдерживаемая форма конструктора варианта получает Type Error, а не Compiler Error.

**Acceptance Scenarios**:

1. **Given** метод с несколькими параметрами, **When** его вызывают именованными аргументами в ином порядке, **Then** каждый параметр получает значение с соответствующим именем.
2. **Given** именованный вызов через интерфейс, **When** форма остаётся неподдерживаемой, **Then** type checker сообщает это до кодогенерации.
3. **Given** именованные аргументы конструктора варианта, **When** язык не предоставляет имён полей варианта, **Then** type checker сообщает, что форма не поддерживается.

### Edge Cases

- Несколько interface-bound'ов включают `Сравниваемое` и пользовательские интерфейсы.
- Один и тот же метод присутствует в нескольких ограничениях; вызов должен сохранять корректный контракт выбранного интерфейса.
- Функции с разным количеством параметров, closure и возвращаемые функции не становятся совместимыми из-за частичного совпадения типов.
- Нельзя смешивать позиционные и именованные аргументы; дублированное или неизвестное имя остаётся диагностикой.
- Запись в поле временного значения и запись по индексу строки не должны обходить проверку допустимой цели.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST отклонять присваивание или передачу функции, если её контракт параметров не гарантирует безопасный вызов в ожидаемом контексте.
- **FR-002**: Система MUST проверять, что цель присваивания допускает запись, и отклонять запись в неизменяемые или неподдерживаемые индексируемые значения до выполнения программы.
- **FR-003**: Система MUST сохранять все заявленные интерфейсные возможности значения, передаваемого в generic-контекст с несколькими interface-bound'ами.
- **FR-004**: Система MUST проверять выполнение каждого interface-bound при generic-вызове и сообщать отсутствующее ограничение.
- **FR-005**: Система MUST позволять вызывать методы конкретных типов с полным набором обязательных именованных аргументов в любом порядке.
- **FR-006**: Система MUST диагностировать неподдерживаемые именованные вызовы на этапе type checking, не оставляя их для Compiler Error.
- **FR-007**: Система MUST сохранять поведение существующих программ с единственным interface-bound, массивами, соответствиями и позиционными аргументами.

## Key Entities

- **Контракт функции**: Набор типов параметров и результата, определяющий, в каких контекстах функцию безопасно вызывать.
- **Ограниченный generic-параметр**: Параметр типа с одним или несколькими обязательными интерфейсными контрактами.
- **Интерфейсная способность значения**: Возможность значения выполнять методы конкретного интерфейса в generic-контексте.
- **Цель присваивания**: Выражение, в которое язык разрешает записывать новое значение.
- **Именованный вызов**: Вызов, сопоставляющий переданные значения параметрам по имени.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% добавленных негативных сценариев для несовместимых функций, записи в строку и неподдерживаемых именованных вызовов завершаются Type Error до кодогенерации или запуска.
- **SC-002**: Все добавленные сценарии с двумя interface-bound'ами, включая вызовы методов каждого bound, выполняются без runtime error.
- **SC-003**: 100% добавленных сценариев корректной записи в массив/соответствие и вызова метода с именованными аргументами проходят без диагностик.
- **SC-004**: Полный обязательный набор проверок проекта проходит без новых регрессий в существующем conformance-корпусе.

## Assumptions

- Функциональные типы будут иметь только те отношения совместимости, которые можно доказать безопасными для всех возможных вызовов; точная стратегия будет зафиксирована в design-плане.
- Несколько interface-bound'ов являются поддерживаемой возможностью языка, а не временным синтаксисом для отклонения.
- Поддержка именованных аргументов для enum-конструкторов требует явного контракта имён полей; до его появления форма будет ранней диагностикой.
- В объём не входят новые формы синтаксиса, изменения публичной семантики `Сравниваемое` или рефакторинг несвязанных частей VM.

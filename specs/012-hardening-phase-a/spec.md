# Feature Specification: Hardening Phase A — embed-диагностики, error-path тесты, nested generic capture, doc-comment hover

**Feature Branch**: `012-hardening-phase-a`
**Created**: 2026-08-18
**Status**: Draft
**Input**: User description: "Составь спецификацию для реализации плана по hardening (`panos-hardening-plan-2026-08-17-verified.md`, Phase A — реально осталось сделать)"

## Контекст

`panos-hardening-plan-2026-08-17-verified.md` перепроверил старый
известный список проблем против живого `HEAD` (не по памяти) и нашёл,
что большинство пунктов уже закрыто параллельной работой в `main`.
Phase A этого плана — четыре пункта, которые остались реально открыты
и оценены как посильные в один заход ("one-sitting"), в порядке
дешевизны:

1. Рендер диагностик недоступен из `panos_embed` (детали:
   `panos-embed-api-followup-plan-2026-08-17.md` §1).
2. Тестовое покрытие `panos_embed` — только happy-path, error-пути не
   протестированы (та же ссылка, §4).
3. Вложенный generic-параметр внутри захватываемого поля closure не
   резолвится рекурсивно в WASM AOT.
4. `///`-doc-комментарии парсятся, но не доходят до LSP hover.

Phase B плана (верификационный проход: `conformance`/`integration`/
`bench`, повторная сверка `ISSUES.md`, flake-перепрогон, fuzz-cron) и
Phase C (архитектурно крупное — актор-scheduler, sandboxing,
metamorphic-тестирование, distinct индекс-типы, явный generic-argument
синтаксис) в эту спецификацию НЕ входят — явно не "one-sitting" по
собственной оценке исходного плана, каждый требует отдельного
research/plan-mode прохода.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Диагностики скрипта видны хосту `panos_embed` (Priority: P1)

Разработчик, встраивающий Panos через `panos_embed` в свой Zig-хост
(например, игровой движок), получает из библиотеки готовую,
отформатированную строку диагностики (`путь:строка:колонка: сообщение`)
для ошибки в загруженном `.pns`-скрипте — без необходимости
переизобретать byte-offset→line/column рендер самому.

**Why this priority**: Любой реальный хост, показывающий
пользователю/разработчику ошибку в скрипте, упирается в это на первом
же некорректном `.pns`-файле. Также устраняет дублирование логики
между `cli/main.zig` и тем, что логически принадлежит `panos_core`.

**Independent Test**: Хост загружает через `panos_embed` скрипт с
намеренной type-ошибкой, вызывает новый публичный API форматирования
диагностик, получает строку, содержащую путь к файлу, номер строки,
номер колонки и текст сообщения — без обращения к `zig/cli/main.zig`.

**Acceptance Scenarios**:

1. **Given** скрипт с синтаксической или type-ошибкой загружен через
   `Runtime.load()`/`.compile()`, **When** хост запрашивает
   форматированные диагностики через публичный API `panos_embed`,
   **Then** возвращается строка вида `путь:строка:колонка: сообщение`
   для каждой диагностики, идентичная по формату той, что сегодня
   печатает `panos` CLI.
2. **Given** диагностика ссылается на файл, отсутствующий в текущем
   графе модулей (например, повреждённое состояние), **When** хост
   запрашивает форматирование, **Then** API возвращает осмысленный
   fallback (не крашится и не паникует), симметрично тому, как CLI уже
   обрабатывает этот случай.
3. **Given** `zig/cli/main.zig` после переноса логики, **When**
   прогоняется существующий набор тестов на формат диагностик CLI,
   **Then** вывод CLI побайтово не меняется.

### User Story 2 - Error-пути `panos_embed` покрыты тестами (Priority: P1)

Разработчик, поддерживающий `panos_embed`, может положиться на тесты,
которые проверяют не только happy-path, но и то, что задокументированные
контракты для ошибочных сценариев действительно выполняются в коде, а
не только на словах в документации.

**Why this priority**: Дёшево реализовать (переиспользует существующую
тестовую инфраструктуру `MemoryReader`), ловит регрессии в контрактах,
на которые сегодня полагается только документация, а не тесты.

**Independent Test**: Каждый из трёх новых тестовых сценариев (сломанный
скрипт, повторный `call()` после runtime-паники, вызов несуществующего
экспорта) проходит независимо от остальных изменений Phase A.

**Acceptance Scenarios**:

1. **Given** скрипт с намеренной синтаксической или type-ошибкой,
   **When** хост вызывает `Runtime.load()`/`.compile()`, **Then**
   вызовы не бросают Zig-error (диагностики доступны только через
   отдельные геттеры), а последующий `call`/`runStart` возвращает
   `error.NotRunnable`/`error.NotCompiled`, не крашится.
2. **Given** успешно скомпилированный и запущенный скрипт, у которого
   один вызов завершился `.runtime_error` (паника внутри скрипта),
   **When** хост вызывает `call()` повторно с другим/тем же экспортом,
   **Then** `Runtime` остаётся в рабочем состоянии и возвращает
   корректный результат (либо поведение явно задокументировано, если
   Runtime намеренно переходит в нерабочее состояние).
3. **Given** скомпилированный скрипт, **When** хост вызывает `call()` с
   именем экспорта, которого не существует, **Then** возвращается
   `error.ExportNotFound`, без паники.

### User Story 3 - Вложенные generic-поля рекурсивно резолвятся в WASM AOT closures (Priority: P2)

Разработчик, пишущий WASM-код с closures, захватывающими значение
generic-типа, чьё СОБСТВЕННОЕ поле тоже является generic-типом (два и
более уровня вложенности), получает рабочий AOT-код вместо диагностики
об отклонении — при условии, что резолюция типа возможна статически.

**Why this priority**: Узкий, явно задокументированный remaining gap
(`concreteCaptureFieldType`'s собственный комментарий подтверждает
ограничение одним уровнем) — не архитектурная переделка, а рекурсия по
уже существующему механизму.

**Independent Test**: Компиляция и AOT-запуск WASM-фикстуры с closure,
захватывающей поле generic-типа, содержащее вложенное generic-поле
(2 уровня), даёт тот же результат, что и native-запуск того же кода.

**Acceptance Scenarios**:

1. **Given** closure захватывает значение типа `Коробка(Коробка(T))`
   (или структурно эквивалентную двухуровневую вложенность generic-поля),
   **When** код компилируется в WASM AOT с конкретным nominal-аргументом
   для `T`, **Then** сборка проходит и рантайм-поведение совпадает с
   native-запуском.
2. **Given** такая же двухуровневая вложенность, но конкретный
   nominal-тип для внутреннего `T` не может быть статически определён,
   **When** код компилируется, **Then** компилятор выдаёт понятную
   диагностику об отклонении (текущее поведение для одноуровневого
   случая, не молчаливый неверный кодогенерация).
3. **Given** уже поддерживаемый одноуровневый generic-захват, **When**
   прогоняется существующий regression-тест на него, **Then** поведение
   не меняется (no regression).

### User Story 4 - Doc-комментарии функции видны в LSP hover (Priority: P3)

Разработчик, наводящий курсор на использование функции/декларации с
предшествующим `///`-doc-комментарием в редакторе с LSP-подключением,
видит текст этого комментария в hover-подсказке вместе с типом — а не
только имя типа.

**Why this priority**: Лексер и парсер уже собирают и сохраняют
doc-комментарии в AST (подтверждено тестом и `grep`), но ни один
компонент дальше по пайплайну их не читает — распарсенные, но мёртвые
данные. Наименее срочный из четырёх пунктов Phase A (не блокирует
корректность программ), но дешёвый и явно недоделанный.

**Independent Test**: LSP hover-запрос на использование функции с
`///`-комментарием перед объявлением возвращает ответ, содержащий и имя
типа, и текст doc-комментария; hover на декларацию без doc-комментария
не регрессирует (по-прежнему возвращает только тип).

**Acceptance Scenarios**:

1. **Given** функция с одной или несколькими contiguous `///`-строками
   непосредственно перед объявлением, **When** LSP-клиент отправляет
   `textDocument/hover` на использование этой функции, **Then** ответ
   содержит текст doc-комментария в дополнение к имени типа.
2. **Given** декларация без `///`-комментария, **When** отправляется
   `textDocument/hover`, **Then** ответ содержит только тип, как и
   сегодня (без регрессии, без пустой/сломанной doc-секции).
3. **Given** decl-вариант AST, у которого поле `.doc` в принципе
   отсутствует (не все варианты декларации его несут), **When**
   выполняется hover на такой декларации, **Then** обработка не
   паникует и не падает, просто не добавляет doc-текст.

### Edge Cases

- Диагностика без валидного `file_id`/`span` (например, диагностика
  уровня графа, не привязанная к конкретному файлу) — форматирование
  не должно паниковать.
- Хост вызывает форматирование диагностик до `load()`/`.compile()`
  (пустой список диагностик) — должен вернуться пустой результат, не
  ошибка.
- `Runtime.call()` вызывается на `Runtime`, который ещё не прошёл
  `runStart` — уже существующий контракт (`error.NotRunnable` и т.п.),
  новые error-path тесты не должны его менять, только фиксировать.
- Nested generic capture глубже двух уровней (три и более) — вне явного
  scope User Story 3, если рекурсивная реализация естественно
  покрывает произвольную глубину — бонус, не обязательное требование;
  если нет — минимум два уровня must work, диагностика на непокрытую
  глубину должна оставаться понятной, не тихим неверным кодом.
- Несколько `///`-блоков подряд с пустой строкой между ними — только
  contiguous блок (без разрывов) непосредственно перед декларацией
  учитывается, как уже определяет лексер сегодня — hover не должен
  вводить новую, отличную от лексера семантику "что считается doc".

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `panos_embed` MUST предоставлять публичный API,
  форматирующий `Diagnostic` в строку `путь:строка:колонка: сообщение`,
  идентичную по формату той, что сегодня выводит `panos` CLI.
- **FR-002**: Логика форматирования диагностик MUST жить в единственном
  месте (`panos_core`), а не дублироваться между `zig/cli/main.zig` и
  `panos_embed`; `zig/cli/main.zig` MUST переиспользовать общую
  реализацию после переноса.
- **FR-003**: `panos_embed` MUST предоставлять helper, который сам
  находит нужный `SourceFile` для диагностики через существующее
  состояние графа модулей — хост не обязан делать этот lookup
  самостоятельно.
- **FR-004**: `panos_embed`'s error-контракты (сломанный скрипт не
  бросает Zig-error; `call()` после `.runtime_error` оставляет `Runtime`
  в задокументированном состоянии; вызов несуществующего экспорта
  возвращает `error.ExportNotFound`) MUST быть покрыты автоматическими
  тестами, не только документацией.
- **FR-005**: WASM AOT-компилятор MUST резолвить конкретный nominal-тип
  для generic-плейсхолдера внутри вложенного generic-поля захватываемого
  значения (минимум два уровня вложенности), когда резолюция статически
  возможна.
- **FR-006**: Когда резолюция вложенного generic-плейсхолдера
  невозможна статически, компилятор MUST выдавать понятную диагностику
  об отклонении, не производить некорректный кодогенерация.
- **FR-007**: LSP `textDocument/hover` MUST включать текст
  contiguous `///`-doc-комментария декларации (если он есть) в ответ,
  в дополнение к уже существующему имени типа.
- **FR-008**: LSP `textDocument/hover` для деклараций без
  doc-комментария или для decl-вариантов без поля `.doc` MUST
  продолжать работать без регрессии и без паники.

### Key Entities

- **Diagnostic**: диагностика компилятора (`message`, `severity`,
  `span{file_id, start, end}`) — сегодня без готовой строки-рендера
  внутри `panos_core`/`panos_embed`.
- **Runtime**: embed-хостом управляемый объект жизненного цикла скрипта
  (`load`/`compile`/`call`/`runStart`) — его error-контракты сегодня
  задокументированы, но частично не протестированы.
- **Захватываемое generic-поле closure**: поле значения generic-типа,
  переносимое в WASM AOT замыкание; сегодня резолвится только на одном
  уровне вложенности плейсхолдера.
- **Doc-комментарий декларации**: contiguous `///`-строки перед
  top-level декларацией, уже собираемые лексером/парсером в
  `token.doc`/AST-поле `.doc`, сегодня не читаемые LSP.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Хост `panos_embed` получает отформатированную строку
  диагностики без обращения к `zig/cli/main.zig` в 100% случаев, где
  сегодня это физически невозможно.
- **SC-002**: Существующие CLI-тесты на формат диагностик проходят без
  изменения ожидаемого вывода после переноса логики.
- **SC-003**: Три новых error-path теста `panos_embed` (сломанный
  скрипт, повторный call после паники, несуществующий экспорт) — все
  зелёные, `zig build test` остаётся зелёным в целом.
- **SC-004**: Фикстура с двухуровневым nested-generic захватом
  компилируется и выполняется в WASM AOT с результатом, идентичным
  native-запуску; ранее поддерживаемый одноуровневый случай не
  регрессирует.
- **SC-005**: Существующий hover-тест LSP расширен фикстурой с
  `///`-комментарием и проверяет присутствие doc-текста в ответе;
  существующие hover-сценарии без doc-комментария продолжают проходить.

## Assumptions

- Scope ограничен ровно четырьмя пунктами Phase A из
  `panos-hardening-plan-2026-08-17-verified.md`; Phase B (верификация)
  и Phase C (архитектурно крупное) в эту спецификацию не входят —
  трактуются как отдельная будущая работа.
- Приоритет реализации внутри Phase A следует порядку дешевизны,
  зафиксированному в исходном плане: диагностики → error-path тесты →
  nested generic capture → doc-comment hover; независимость User Stories
  друг от друга позволяет менять порядок при необходимости.
- User Story 3 (nested generic capture) ограничивается статически
  резолвируемыми случаями; произвольная глубина — bonus, не жёсткое
  требование (см. Edge Cases).
- User Story 4 (doc hover) не расширяется на `completion` в рамках этой
  спецификации — план явно называет это опциональным, отдельным,
  аддитивным шагом после hover.
- `panos_embed`'s reset/reload API (§2) и sandboxing (§3) из
  `panos-embed-api-followup-plan-2026-08-17.md` НЕ входят в эту
  спецификацию — исходный hardening-план прямо ссылается на них по
  оригинальному приоритету, но Phase A ограничен только §1 и §4 того
  документа.

# Data Model: Явный generic-argument синтаксис

Никаких новых персистентных структур/AST-форм — фича работает целиком
поверх уже существующих `Index_Expr`/`Tuple_Expr`/`generic_function_parameters`/
`substitutions`-карты. Таблицы ниже документируют СУЩЕСТВУЮЩИЕ структуры,
задействованные новой логикой, и правило реинтерпретации между ними.

## Реинтерпретация `Index_Expr` → explicit generic-вызов

| Синтаксис | AST (сегодня, без изменений) | Условие реинтерпретации |
|---|---|---|
| `ф[Тип](...)` | `Call_Expr{ callee: Index_Expr{ object: ф, index: Тип-выражение } }` | `expr_symbols.get(index.object)` резолвится в символ, для которого `generic_function_parameters.get(symbol)` непусто. |
| `ф[(Т1, Т2)](...)` | `Call_Expr{ callee: Index_Expr{ object: ф, index: Tuple_Expr{elements: [Т1, Т2]} } }` | То же условие; `index.index` — `.tuple`, элементы — explicit-аргументы по порядку. |
| `модуль.ф[Тип](...)` | `Call_Expr{ callee: Index_Expr{ object: Property_Expr{object: модуль, property: "ф"}, index: Тип } }` | То же условие, `index.object` — `Property_Expr`, не `Ident_Expr`; символ резолвится так же (`expr_symbols` не различает квалифицированные/неквалифицированные ссылки на этом уровне). |
| `ф[X](...)`, `ф` — обычное indexable значение | То же дерево | Условие НЕ выполняется (`generic_function_parameters` пусто/нет символа) → существующий путь без изменений. |

## `resolveTypeFromExpr` — Expr-форма → `types.TypeId`

| `Expr`-вариант | Обрабатывается как | Результат при неуспехе |
|---|---|---|
| `.ident{name}` | Имя типа (generic-параметр текущей функции / builtin / user-defined nominal) | `null`, если имя не резолвится ни в один из трёх источников (уже репортит диагностику само, как `resolveType`). |
| `.property{object: .ident, property}` | Квалифицированное имя типа (`модуль.Тип`) | `null`, если `object` не `.ident`, или квалифицированный символ не найден. |
| `.call{callee, arguments}` | Generic-инстанциация (`Тип(Аргумент, ...)`) | `null`, если `callee` не резолвится в тип-имя, или любой `arguments[i]` рекурсивно вернул `null`. |
| Всё остальное (`.number`, `.binary`, `.call` с не-типовым callee и т.п.) | — | `null` — форма в принципе не типовидна (FR-007). |

## Substitutions-карта — точка встречи explicit и inferred

| Состояние карты | Источник записи | Дальнейшее поведение |
|---|---|---|
| Предзасеяна explicit-значением (`parameter.typ -> resolved_type`) | Новая `.index`-ветка, ДО обычного цикла вывода из аргументов | Обычный цикл (`inferGenericSubstitution` по каждому аргументу) видит уже существующую запись — при совпадении молчит, при конфликте репортит "type-параметр выведен неоднозначно" (существующий код, `type_checker.zig:5945-5947`), без новой логики. |
| Пуста (нет explicit-аргумента) | — | Поведение не меняется (FR-008) — inferred из аргументов/`expected_return`, при отсутствии контекста — `unconstrained`, при наличии `expected_return` без результата — диагностика "не удалось вывести type-параметр". |

## Инвариант

Реинтерпретация строго ОДНОНАПРАВЛЕННАЯ и решается ровно один раз, на
входе в `.index`-ветку callee-switch'а — она никогда не "откатывается"
обратно к обычной индексации после того, как символ подтверждён
generic-функцией (FR-006 гарантирует обратное: для НЕ-generic
объектов индексации реинтерпретация вообще не запускается, не
"пробуется и откатывается").

# Feature Specification: Явный generic-argument синтаксис

**Feature Branch**: `013-explicit-generic-args`
**Created**: 2026-08-18
**Status**: Draft
**Input**: User description: "Явный generic-argument syntax `ф[Тип](...)` — последний недостающий кусок из sound-core type-system плана (`project_panos_sound_core_typesystem_direction`). Сегодня, если вывод типа не может определить `T` из контекста аргументов/return-типа, единственный исход — диагностика `\"не удалось вывести type-параметр 'T'\"` без способа явно указать `T` вручную."

## Контекст

`panos-hardening-plan-2026-08-17-verified.md` Phase C называет это самым
ценным, но и самым крупным пунктом списка: без него нельзя убрать
последний permissive fallback typechecker'а — при отсутствии
`expected_return` неразрешённый `T` тихо становится `unconstrained`
(`zig/core/type_checker.zig:4587-4589` и три структурно идентичных места
на строках ~4692/5232/5465/5826) вместо диагностики, и реальный код
(`panosiki/cli-selector`'s `выборка.новый_селектор(...)`) на это
полагается.

**Реальный грамматический конфликт, найденный при research этой
спецификации**: предложенный в исходном плане синтаксис `ф[Тип](...)`
текстово идентичен уже существующей, рабочей форме «индексация, потом
вызов» (`массив_функций[0](args)`, парсится как `Call_Expr{ callee:
Index_Expr{ object, index } }`, `zig/core/parser.zig:1696`
`parseIndex`). У парсера нет бэктрекинга (архитектурное ограничение,
подтверждённое ранее в `specs/005-language-fixes`) — на этапе парсинга
невозможно узнать, generic ли `ф`, значит невозможно на месте решить,
означают ли скобки индекс или type-аргумент.

**Принятое решение** (по образцу Go, `go/parser`+`go/types`): не менять
грамматику вообще — `ф[X](...)` продолжает парситься СЕГОДНЯШНИМ путём
(`Index_Expr` внутри `Call_Expr`), никакого нового токена/сигила.
Неоднозначность разрешается ПОЗЖЕ, в резолвере/тайпчекере: когда
становится известно, что `ф` — generic-функция (не indexable
значение), тайпчекер реинтерпретирует уже построенный `Index_Expr` —
его `index`-поддерево (обычный `Expr`) механически превращается в
`TypeNode`, если его форма «типовидна» (`.ident` → `TypeNode.ident`,
`.property`-цепочка через точку → `TypeNode.qualified`, `.call` над
одной из этих форм → `TypeNode.generic`/`.qualified` с параметрами).
Это НЕ бэктрекинг (ни перемотки токенов, ни повторного парсинга) — то
же дерево, другой смысл, определяемый после того как известна
семантика `ф`. Когда `ф` — обычное indexable значение (не generic
функция), поведение `Index_Expr`+`Call_Expr` не меняется НИ БАЙТОМ —
реинтерпретация строго условна.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Явное указание generic-типа при отсутствии контекста (Priority: P1)

Разработчик вызывает generic-функцию, чей type-параметр не выводим ни
из аргументов, ни из ожидаемого return-типа (например, `Тип(T)` —
результат нигде не присваивается типизированной переменной), и
указывает `T` явно вместо получения диагностики "не удалось вывести
type-параметр".

**Why this priority**: Это единственная причина существования фичи —
закрывает последний permissive fallback typechecker'а, на который
сегодня code полагается только потому, что явного способа нет.

**Independent Test**: Программа с `функ ф[T](x: Строка) -> Тип(T)`,
вызванная как `ф[Число]("42")` без какой-либо типизированной привязки
результата, компилируется и возвращает значение типа `Тип(Число)`;
без явного `[Число]` в том же контексте (без `пер x: Тип(Число) = ...`)
сегодня либо тихо получает `unconstrained`, либо (если
`expected_return` где-то всё же есть) — диагностику.

**Acceptance Scenarios**:

1. **Given** generic-функция, чей type-параметр присутствует ТОЛЬКО в
   return-типе, **When** её вызывают с явным `ф[Тип](...)` без
   типизированной привязки результата, **Then** компиляция проходит, а
   result-выражение имеет тип, подставленный из явного аргумента.
2. **Given** та же функция, **When** её вызывают БЕЗ явного
   type-аргумента и без контекста, откуда `T` выводим, **Then**
   поведение не меняется относительно сегодняшнего (см. Assumptions —
   не превращать существующий permissive fallback в ошибку этой
   спецификацией).
3. **Given** `ф[Тип](...)`, **When** `ф` — НЕ generic-функция, а
   обычное indexable значение (массив/соответствие функций), **Then**
   поведение идентично сегодняшнему (`ф[Тип]` — индекс, `(...)` —
   вызов результата), без регрессии, без новой диагностики.

---

### User Story 2 - Явный конфликтующий с выводом аргумент — понятная ошибка (Priority: P1)

Разработчик указывает явный type-аргумент, который противоречит типу,
реально переданному в аргументах вызова, и получает понятную
диагностику вместо тихого несоответствия.

**Why this priority**: Без этого явный аргумент — ловушка: код
компилируется, но подставляет не тот тип, что реально течёт через
аргументы, воспроизводя ровно тот класс runtime-несоответствий, что
typechecker существует, чтобы предотвращать.

**Independent Test**: `функ ф[T](x: T) -> T`, вызванная как
`ф[Число]("текст")` (явный `Число`, аргумент — `Строка`) даёт Type
Error на этапе typecheck, не runtime-ошибку и не тихую подстановку.

**Acceptance Scenarios**:

1. **Given** явный type-аргумент и аргумент вызова, чей выведенный тип
   ему противоречит, **When** программа компилируется, **Then**
   typechecker сообщает Type Error до кодогенерации.
2. **Given** явный type-аргумент, совпадающий с тем, что и так вывелся
   бы из аргументов (избыточный, но не противоречащий), **When**
   программа компилируется, **Then** компиляция проходит как обычно.

---

### User Story 3 - Явный type-аргумент нетиповидной формы — понятная ошибка (Priority: P2)

Разработчик пишет `ф[выражение](...)`, где `ф` — generic-функция, а
`выражение` — синтаксически не может обозначать тип (например,
`ф[1 + 2](...)`), и получает понятную диагностику вместо того, чтобы
это молча трактовалось как обычная индексация с последующим ошибочным
вызовом.

**Why this priority**: Реинтерпретация `Index_Expr` в тип-ссылку
работает только для конечного набора форм (`.ident`/`.property`-цепочка/
`.call` над ними) — нужна явная граница, а не тихий сбой в
"попытка индексировать функцию" где-то дальше по пайплайну.

**Independent Test**: `ф[1 + 2](...)` с `ф`, реально резолвящейся в
generic-функцию, даёт понятную diagnostic-строку, упоминающую, что
явный type-аргумент ожидает имя типа, не произвольное выражение — не
крашится, не даёт непонятную ошибку про индексацию функции.

### Edge Cases

- `модуль.ф[Тип](...)` — квалифицированный вызов generic-функции из
  другого модуля с явным типом; та же реинтерпретация должна работать
  через `Index_Expr{ object: Property_Expr{...} }`.
- Несколько type-параметров: `функ ф[T, U](...)` вызванная явно —
  `ф[(A, B)](...)` через существующую `Expr.tuple`-форму внутри
  скобок индексации, см. Assumptions — не требует изменений
  грамматики `Index_Expr` самой по себе.
- Явный type-аргумент на generic-МЕТОДЕ (`это.метод[Тип](...)`), не
  только свободной функции — то же дерево (`Index_Expr` над
  `Property_Expr`), нужно подтвердить, что метод-вызовы вообще
  поддерживают generic-параметры сегодня (если нет — вне scope, метод
  generics — отдельная возможность языка).
- Явный type-аргумент на конструкторе варианта перечисления/структуры,
  если такие когда-либо станут generic по своим ЯВНЫМ аргументам
  (не по инстанциации типа) — сегодня вне scope, конструкторы уже
  типизируются через `Тип(Аргумент)` на уровне ТИПА, не вызова.
- `x как Тип` (существующий cast) и `ф[Тип](...)` синтаксически не
  пересекаются (разные ключевые конструкции) — подтвердить, что
  добавление реинтерпретации не меняет прецедентность/парсинг cast'а.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Typechecker MUST принимать `ф[Тип1, Тип2, ...](...)` —
  вызов generic-функции (свободной, квалифицированной через модуль,
  или generic-метода, если методы поддерживают generic-параметры) с
  одним или несколькими явными type-аргументами, синтаксически
  выраженными как индексация с последующим вызовом.
- **FR-002**: Явные type-аргументы MUST подставляться в
  type-параметры функции В ОБЪЯВЛЕННОМ порядке.
- **FR-003**: Typechecker MUST отклонять вызов Type Error'ом, если
  количество явных type-аргументов не совпадает с количеством
  объявленных type-параметров функции.
- **FR-004**: Typechecker MUST отклонять вызов Type Error'ом, если
  явный type-аргумент противоречит типу, реально выводимому из
  аргументов вызова или ожидаемого return-типа (явный аргумент не
  переопределяет молча уже согласованный вывод — конфликт есть
  конфликт).
- **FR-005**: Typechecker MUST отклонять вызов Type Error'ом, если
  явный type-аргумент нарушает interface-bound, объявленный на
  type-параметре (та же проверка, что сегодня уже есть для выведенных
  substitutions).
- **FR-006**: Когда `ф` (объект индексации) резолвится НЕ в
  generic-функцию (обычное indexable значение — массив, соответствие,
  и т.п.), поведение `Index_Expr`/`Call_Expr` MUST оставаться
  побайтово идентичным сегодняшнему — реинтерпретация не должна менять
  ни синтаксис, ни семантику существующего "индекс, потом вызов"
  паттерна.
- **FR-007**: Когда `ф` резолвится в generic-функцию и `[...]`
  содержит форму, которая не может обозначать тип (произвольное
  runtime-выражение — арифметика, вызов не-типовой функции и т.п.),
  typechecker MUST сообщить понятную диагностику, отличимую от обычной
  "попытка индексировать функцию", а не молча падать в
  непредсказуемое поведение.
- **FR-008**: Существующий permissive fallback (неразрешённый `T` без
  контекста → `unconstrained`, БЕЗ ошибки, `zig/core/type_checker.zig`'s
  4 структурно идентичных места) MUST оставаться поведением ПО
  УМОЛЧАНИЮ при отсутствии явного type-аргумента — эта спецификация
  добавляет способ явно указать `T`, не меняет то, что происходит,
  когда его не указали.

### Key Entities

- **Явный type-аргумент**: содержимое `[...]` вызова generic-функции,
  синтаксически — обычное выражение (`Expr`), семантически (только
  когда объект индексации — generic-функция) переинтерпретируемое как
  `TypeNode`.
- **Реинтерпретируемая форма**: подмножество `Expr`-форм, механически
  превратимых в `TypeNode` — голый идентификатор, точечная цепочка
  (квалифицированное имя), вызов над одной из этих форм (инстанциация
  с параметрами). Любая другая форма — не type-аргумент, а обычное
  выражение (см. FR-006/FR-007 для того, как это различается по
  контексту).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% добавленных сценариев с явным type-аргументом на
  функции, чей `T` сегодня недовыводим (только в return-типе, нет
  `expected_return`), компилируются и дают корректный результат-тип —
  без явного аргумента тот же вызов остаётся ровно тем поведением, что
  есть сегодня (unconstrained/поглощение).
- **SC-002**: 100% добавленных сценариев с конфликтующим явным
  аргументом дают Type Error до кодогенерации.
- **SC-003**: 100% добавленных сценариев `ф[X](...)`, где `ф` — НЕ
  generic-функция, проходят существующий regression-набор для
  индекс-потом-вызов без единого изменения ожидаемого поведения.
- **SC-004**: Полный обязательный набор проверок проекта (`zig build
  test`/`conformance`/`aot`/`lsp`/`browser`) проходит без новых
  регрессий.

## Assumptions

- Синтаксис — `ф[Тип](...)` / `ф[Тип1, Тип2](...)`, без нового
  токена/сигила: переиспользует существующую `Index_Expr`+`Call_Expr`
  грамматику, разрешая неоднозначность на семантическом этапе (по
  образцу Go), не на этапе парсинга. Решение зафиксировано в ходе
  research этой спецификации — альтернативы (`::<>`/`::[]`) отклонены
  как ненужное усложнение грамматики при наличии более простого пути.
- `Index_Expr` сегодня несёт ОДИН `index: ExprId` — расширять его до
  списка ради нескольких явных type-аргументов не нужно: `Expr.tuple`
  (`(a, b, ...)`, уже существующая, отдельно парсящаяся форма,
  `zig/core/ast.zig:227`) переиспользуется как контейнер — `ф[(A,
  B)](...)` парсится СЕГОДНЯШНЕЙ грамматикой (`Index_Expr{ index:
  Tuple_Expr{elements: [A, B]} }`), реинтерпретация распаковывает
  `.tuple.elements` в список type-аргументов вместо одиночного
  элемента. Одиночный случай (`ф[Тип](...)`) не заворачивается в
  кортеж. Нулевые изменения в парсере/`Index_Expr`-consumers ради
  arity — весь новый код живёт в семантической реинтерпретации.
- Явный generic-argument syntax на generic-МЕТОДАХ входит в scope,
  только если методы уже поддерживают собственные (не связанные с
  типом получателя) type-параметры сегодня — если это не так, метод-
  часть Edge Cases остаётся нереализованной документированной
  границей, не блокирует US1/US2 (свободные и квалифицированные
  функции).
- Не входит в scope: явные type-аргументы для enum/struct-конструкторов
  (`Тип(Аргумент)` уже покрывает это на уровне типа, не вызова), любое
  изменение существующего `x как Тип` cast'а.

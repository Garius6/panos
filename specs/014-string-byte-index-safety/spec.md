# Feature Specification: Устранение рановый/байтовый index-путаницы

**Feature Branch**: `014-string-byte-index-safety`
**Created**: 2026-08-19
**Status**: Done
**Input**: User description: "Distinct рановый/байтовый index-типы — из Phase C hardening-плана (`panos-hardening-plan-2026-08-17-verified.md`)"

## Контекст

`строки.найти`/`строки.срез` возвращают/принимают РАНОВЫЙ индекс.
`строки.байт`/`строки.длина_байт`/`строки.срез_байт` работали с БАЙТОВЫМ
индексом. Оба типизировались одинаково — голым `Целое` — ничто не
мешало передать рановый индекс в байтовую функцию. Подтверждённый
реальный случай: `"купить хлеб"` (кириллица, 2 байта/руна в UTF-8) →
`"купит�"` — срез по не-рановой границе тихо портит текст.

## Рассмотренные дизайны (research этой сессии)

- **A: Primitive-enum newtype** (как `Число`/`Целое`) — новые варианты
  `types.Primitive`, exhaustive switch на нём разбросан по 5 файлам
  компилятора.
- **B: Nominal struct-обёртка** в прелюде — требует нового, ранее не
  существовавшего в кодовой базе механизма (аллокация `Aggregate`
  напрямую из native builtin, не через `.build_struct` bytecode).
- **C (выбран): Go-стиль** — у Go нет rune-индексного API вообще;
  `strings.Index`/`s[i:j]` всегда байтовые, rune-работа — через `[]rune`
  (другой ТИП). Байтовые примитивы `строки.байт`/`длина_байт`/
  `срез_байт` УБРАНЫ со `Строка` целиком (не задепрекейчены — удалены);
  байтовая работа теперь идёт через уже существующие `строки.в_байты(s)
  -> Массив(Целое)` + обычные методы массива (`.длина()`/`.получить()`/
  `.срез()` — все три уже существовали, `.срез()` уже был реализован и
  для native, и для WASM AOT, новый builtin вообще не понадобился).
  Рановый индекс живёт только в контексте `Строка`, байтовый — только
  в контексте `Массив` — смешать физически негде, без единого нового
  типа в языке.

## Реальный blast radius (расходится с изначальной оценкой)

Первая оценка (грep по `найти`/`срез`/`срез_байт`/`длина_байт` разом) —
77 вызовов в 9 репозиториях (panos + 8 `panosiki/*`). После выбора
дизайна C выяснилось: РАНОВЫЙ API (`найти`/`срез`) не менялся вообще —
именно он использовался во всех `panosiki/*` вызовах. БАЙТОВЫЙ API
(единственное, что реально удалено) использовался ТОЛЬКО в этом
репозитории: `std/архив.pns` (18 вызовов, tar-парсер) и
`std/кодирование/экранирование.pns` (2 вызова). `panosiki/*` не
затронут вообще — реальный scope оказался на два порядка меньше
изначальной оценки.

## Что сделано

- `zig/core/resolver.zig`: `байт`/`длина_байт`/`срез_байт` убраны из
  обоих списков экспортов модуля `строки`.
- `zig/core/type_checker.zig`: три `isBuiltinModule(..., "строки", ...)`
  блока удалены.
- `zig/core/compiler.zig`: три записи из call-builtin таблицы удалены.
- `zig/core/bytecode.zig`: три opcode-варианта (`str_byte`/
  `str_len_bytes`/`str_slice_bytes`) удалены.
- `zig/core/vm.zig`: три native-реализации (`strByte`/`strLenBytes`/
  `strSliceBytes`, включая UTF-8-граница-guard в `strSliceBytes`,
  добавленный раньше как раз против этого класса бага) удалены — вместе
  с dispatch-веткой.
- `zig/core/mir_lowering.zig`/`wasm_emit.zig`/`wasm_strings.zig`: WASM
  AOT lowering для `длина_байт` убран (`байт`/`срез_байт` в AOT никогда
  не поддерживались — нечего было убирать); `buildByteLength`
  runtime-функция и её `StringRuntime.byte_length` поле удалены как
  ставшие мёртвым кодом.
- `std/архив.pns`: 18 сайтов переписаны на `строки.в_байты(s)` +
  `.длина()`/`.получить()`/`.срез()`. Подтверждено сквозным smoke-тестом
  (`архив.собрать`/`.разобрать` round-trip с кириллическим содержимым —
  данные не побились).
- `std/кодирование/экранирование.pns`: 2 сайта переписаны аналогично.
  Подтверждено через `json.сериализовать` (табы/кавычки экранируются
  корректно).
- `docs/src/language/basic-types.md` §"Байты" и
  `docs/src/language/standard-library.md` §"архив: tar" переписаны под
  новый паттерн.
- `tests/wasm/aot_strings_test.zig`/`aot_gc_arena_test.zig`: два теста,
  прямо использовавших `строки.длина_байт`, обновлены (byte-length
  assertion убрана из AOT-теста — `строки.в_байты` сам по себе не
  поддержан в WASM AOT, отдельный, не связанный с этой миграцией
  pre-existing gap; `aot_gc_arena_test` переключён на `длина(s)` —
  ему было важно любое `Целое`-выражение, не конкретно байтовое).

## Проверено

`zig build test`/`conformance`/`aot`/`integration`/`lsp`/`browser` —
все зелёные. Ручные smoke-тесты через `./zig-out/bin/panos`: полный
tar round-trip с кириллическим содержимым, JSON-экранирование
управляющих символов.

## Вне scope

- `panosiki/*` — не тронуто, байтового API там не было.
- `строки.в_байты` в WASM AOT — pre-existing, не связанный с этой
  задачей gap (не поддержан ни до, ни после); если понадобится —
  отдельная задача.
- Рановый vs байтовый индекс для МАССИВОВ произвольного содержимого
  (не строк) — вне контекста этой находки, там индекс всегда один вид.

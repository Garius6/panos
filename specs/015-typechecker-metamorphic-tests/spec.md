# Feature Specification: Metamorphic-тестирование typechecker'а

**Feature Branch**: `015-typechecker-metamorphic-tests`
**Created**: 2026-08-19
**Status**: Done
**Input**: User description: "Metamorphic-тестирование typechecker'а — Phase C hardening-плана (`panos-hardening-plan-2026-08-17-verified.md`)"

## Контекст

Crash-oracle fuzzing (`zig build fuzz`, seed-corpus проход уже
встроен в `zig build test`, continuous `--fuzz` режим сломан на этом
Zig-тулчейне — см. `project_panos_zig_fuzz_continuous_broken` память)
проверяет только "не упало ли". Реальный класс багов, что чинился в
этом проекте (ложный дубликат-вариант match-arm'ов, `Сравниваемое` вне
generic-контекста, неверный тип `получить()`, и т.д.) — тихо
НЕПРАВИЛЬНЫЙ ответ, не крах. Нужен другой oracle: два семантически
эквивалентных варианта исходника должны давать ОДИНАКОВОЕ количество и
severity-состав диагностик.

Unparser/pretty-printer в кодовой базе нет (`grep` подтвердил) —
трансформации не AST-мутация с реprint, а прямые пары ИСХОДНОГО ТЕКСТА,
написанные вручную (не байты-мутатор) — по одной на каждый из 5
инвариантов, задокументированных в исходном hardening-плане.

## Реализация

`zig/core/type_checker.zig` — новый helper
`expectEquivalentDiagnostics(label, variant_a, variant_b)`: гоняет оба
варианта через полный lexer→parser→resolver→check пайплайн, сравнивает
СУММУ ошибок и предупреждений (не точное количество на фазу и не текст
сообщений — только severity-мультимножество, устойчиво к
несущественным различиям в формулировках между вариантами) через оба
`resolved.diagnostics`/`checked.diagnostics`.

5 test-блоков, каждый — прямая, минимальная реализация одного
инварианта из плана:

1. **Untyped `пер x = ...` vs typed `пер x: T = ...`** — `выбор`
   внутри `Массив(T)`-возвращающей функции напрямую vs через
   промежуточную типизированную привязку.
2. **Порядок именованных аргументов конструктора** — `Т(x=1, y=2)`
   vs `Т(y=2, x=1)`.
3. **Порядок независимых top-level деклараций** — две функции,
   переставленные местами.
4. **Метод через конкретный тип напрямую vs через interface-типизированную
   переменную** — тот же `.показать()`-вызов, разный статический тип
   переменной-получателя.
5. **Порядок непротиворечащих match-arm'ов** — два разных (не
   дублирующих) паттерна одного `перечисление`, переставленные местами.

## Результат

Все 5 пар прошли ЧИСТО с первого прогона (0 расхождений) — подтверждает,
что предыдущие фиксы (type-checker-hardening батч, match-arm
exhaustiveness) уже закрыли эти конкретные инварианты. Ценность —
не в том, что что-то нашли ПРЯМО СЕЙЧАС, а в том, что эти 5 инвариантов
теперь под regression-guard: если любой из них снова сломается,
`zig build test` красный, а не тихая порча где-то в проде.

## Вне scope

- Байты-мутатор/genuinely fuzzed-трансформации (план предполагал
  `std.testing.fuzz`-таргет) — не реализовано: `--fuzz` (continuous)
  сломан на тулчейне, а seed-corpus-only версия для metamorphic-пар
  (в отличие от crash-oracle) не даёт дополнительной ценности без
  автоматической генерации новых пар — 5 вручную написанных пар решают
  ту же задачу дешевле для текущего масштаба находок.
- Расширение до большего числа инвариантных пар — можно добавлять по
  мере находки новых классов багов, тем же паттерном
  (`expectEquivalentDiagnostics`).

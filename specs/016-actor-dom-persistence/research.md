# Research: Актор переживает между DOM-событиями (WASM AOT)

## Контекст

Последний открытый пункт из `panos-hardening-plan-2026-08-17-verified.md`
Phase C — `Процесс`-захват в DOM-closure сегодня явно отклоняется
(`mir_lowering.zig:3029-3030`, `classifyCaptureDepth`'s `.process =>
.unsupported`): "AOT handle указывает на actor frame в сбрасываемой
арене, а Phase 1 scheduler не сохраняет актор между DOM-вызовами".

## Архитектура сегодня (вычитано полностью, не предполагается)

### Память: две зоны (`wasm_gc_arena.zig`, Phase 1 GC)

- **Global 0** — обычная bump-арена. Сбрасывается на чекпоинт в НАЧАЛЕ
  каждого JS-вызываемого entry-point'а (`старт`, любой
  `module.dom_handler_names`) и восстанавливается при возврате
  (`wrapEntryPoint`). Всё, что там живёт, гарантированно мертво к
  следующему вызову.
- **Globals 1/2** — permanent-регион (bump-указатель + неизменяемый
  потолок), НЕ сбрасывается. Уже используется для значений, захваченных
  DOM click-замыканиями через границу вызовов (Строка/struct capture,
  Stage C — `wasm_heap.findOrBuildAllocPermanent`,
  `promoteStructToPermanent` в `mir_lowering.zig`).

Актор сегодня аллоцируется через `wasm_heap.findOrBuildAlloc`
(`wasm_actors.zig:134`) — **обычную, сбрасываемую арену**. Это
буквально единственная причина проблемы: не архитектурный тупик, а
"использована не та из двух уже существующих аллокаций".

### Один актор = одна аллокация (mailbox инлайн)

`wasm_actors.zig`'s `buildPop`/`buildHas` читают/пишут mailbox-кольцо
через `frame_load`/`frame_store` по ФИКСИРОВАННЫМ byte-offset'ам
ОТНОСИТЕЛЬНО frame-указателя актора (`ring_base_slot`/`head_slot`/
`count_slot` — те же слоты, что несут CPS resume-state). Mailbox —
НЕ отдельная scheduler-структура, а часть ОДНОЙ аллокации фрейма.
Значит "промоутить актора в permanent" — одна операция копирования
блока байт (тот же паттерн, что `promoteStructToPermanent`), не
распределённая правка нескольких структур.

### `Процесс`-значение = голый указатель на фрейм

`expandSpawn` (`wasm_actors.zig:220-338`): `.spawn`'s `dst` — это
`layout.ptr_type` (`i32`) значение, результат `alloc(target_total_slots
* 8)`. Захват `Процесс` DOM-замыканием структурно ничем не отличается
от захвата любого другого указателя (Строка/структура) — та же форма
проблемы, что Stage C уже решил для других типов.

### Scheduler — не переживающий между вызовами цикл, а ОДНОРАЗОВЫЙ прогон внутри `старт()`

`buildScheduler` (`wasm_actors.zig:429-517`) полностью ПЕРЕПИСЫВАЕТ
`старт()`: аллоцирует frame0 (process 0 = старт), гоняет ДО 16
развёрнутых раундов (`emitSchedulerRound`, unrolled if/else diamond,
никакого настоящего WASM `loop`) — process 0 и (если заспавнен) process
1 — пока `done0` не станет true, затем читает `mir_cps.result_slot` из
frame0 и ВОЗВРАЩАЕТСЯ. Раунды НЕ переживают между отдельными JS→WASM
вызовами — это самодостаточный синхронный прогон, целиком внутри
одного вызова `старт()`. Explicit Phase-1 constraint (тот же файл,
шапка): максимум ОДИН `.spawn` на весь модуль, и он должен быть
достижим из `старт()`'s собственного CPS-тела.

## Почему это НЕ "нужен общий переиспользуемый N-акторный scheduler"

Первое впечатление (до вычитки) — что нужен полноценный дизайн
персистентного, реентерабельного планировщика. После вычитки: реальный
мотивирующий сценарий (Elm-архитектура — одна модель-актор, UI-события
как сообщения, см. `project_panos_elm_architecture_dom_storage_design`)
укладывается в УЖЕ существующее "максимум один spawn" ограничение.
Не нужно снимать это ограничение и не нужна произвольная топология
множества акторов — нужно ровно: **тот единственный актор, что уже
спавнится в `старт()`, должен пережить возврат из `старт()` и принимать
сообщения из последующих отдельных вызовов (DOM-хендлеров)**.

## Предлагаемый (суженный) дизайн

1. **Промоушен фрейма актора в permanent при захвате DOM-замыканием** —
   новая `promoteActorFrameToPermanent` в `mir_lowering.zig`, тем же
   паттерном, что `promoteStructToPermanent`: копирует
   `target_total_slots * 8` байт (размер уже известен на этапе `.spawn`-
   лоуэринга) в permanent-регион, возвращает новый указатель.
   `classifyCaptureDepth`'s `.process => .unsupported` заменяется на
   реальную классификацию + промоушен вместо отказа.
2. **Мини-раунды из точки повторного входа** — DOM-хендлер, вызывающий
   `отправить(actor, сообщение)` (или неявно требующий ответа через
   `ждать`/`выбор ожидание`), не может звать `buildScheduler`'s цикл
   (тот принадлежит уже завершившемуся `старт()`). Нужна отдельная,
   вызываемая из ТЕЛА хендлера последовательность раундов, переиспользующая
   ТОЛЬКО "process 1"-половину `emitSchedulerRound` (актор уже
   заспавнен и живёт в permanent — `child_frame_slot`-проверка на
   "заспавнен ли" тривиально true) — без process-0-половины, без
   зависимости от старого `frame0` (`старт`'s фрейм уже мёртв, не
   промоутился и не должен).
3. **Bounded rounds per re-entry, не единый глобальный бюджет** —
   каждый ВЫЗОВ хендлера получает свой собственный лимит раундов (та же
   `scheduler_rounds = 16` константа, или отдельная, подбираемая
   эмпирически) — не общий счётчик через все вызовы жизни программы.
4. Phase-1 constraint (максимум один `.spawn`, `старт` обязан содержать
   `получить()`) — **оставить как есть**, не расширять в этом проходе.

## Открытые вопросы (нужно подтверждение перед кодом)

- **Что если DOM-хендлер не ждёт ответа, просто шлёт fire-and-forget?**
  Сегодняшний `отправить`/`.send` синхронный на panos-уровне (кладёт в
  mailbox), но ФАКТИЧЕСКАЯ обработка актором происходит только когда
  ЕГО step-функция реально прогоняется раундом. Нужно решить: гонять
  раунды актора СРАЗУ после каждого `отправить` внутри хендлера
  (простой, предсказуемый вариант — сообщение обработано до возврата из
  хендлера), или откладывать (сложнее, не покрыто вычиткой).
  Рекомендация: гонять сразу, симметрично тому, как `старт()` уже
  работает.
- **Что если старый resettable-арена-фрейм актора (созданный ВНУТРИ
  `старт()`'s исходного прогона) уже начал использоваться ДО момента
  захвата DOM-замыканием, а промоушен происходит только В МОМЕНТ
  построения замыкания?** Нужно подтвердить порядок: замыкание строится
  ПОСЛЕ `запусти`/`.spawn` (естественный порядок кода — сначала
  спавним, потом регистрируем хендлер, использующий актора) — если это
  всегда так, промоушен в момент построения closure box'а безопасен
  (актор ещё не успел накопить mailbox-состояние, которое надо было бы
  переносить отдельно от фрейма — но раз mailbox инлайн в том же
  блоке, это не проблема даже если накопил).
- **Лимит раундов при повторном входе** — использовать ту же константу
  16, или что-то меньшее (одно сообщение — обычно 1-2 раунда, не 16)?
  Не критично, но стоит решить явно, не унаследовать бездумно.

## Оценка объёма

Меньше, чем изначально оценивалось в hardening-плане ("реальная
архитектурная работа, отдельный research/plan-mode проход") — но всё
ещё реальная работа, не "one-sitting": новая функция промоушена в
`mir_lowering.zig`, новая точка входа "прогнать раунды актора" в
`wasm_actors.zig` (вызываемая из хендлер-лоуэринга, не из
`buildScheduler`), плюс снятие `.process => .unsupported` в
capture-классификации, плюс тесты (реальный wasmtime-прогон: `старт`
спавнит актор, регистрирует click-хендлер с захватом, СИМУЛИРОВАННЫЙ
повторный вызов хендлера шлёт сообщение и читает ответ).

# Feature Specification: Актор переживает между DOM-событиями (WASM AOT)

**Feature Branch**: `016-actor-dom-persistence`
**Created**: 2026-08-19
**Status**: Done — US1 and US2 both implemented and tested (see "Статус реализации" ниже)
**Input**: User description: "Актор-scheduler между DOM-событиями — последний открытый пункт Phase C hardening-плана"

## Контекст

См. `research.md` для полной архитектурной вычитки. Резюме: `Процесс`
в WASM AOT — голый указатель на фрейм (mailbox инлайн в той же
аллокации), сегодня всегда в сбрасываемой арене. DOM-closure capture
явно отклоняется (`mir_lowering.zig`, `.process => .unsupported`).
Scheduler (`buildScheduler`) — одноразовый синхронный прогон целиком
внутри `старт()`, не переживающий между вызовами структурно. Реальный
мотивирующий сценарий (один персистентный актор-модель, DOM-события
как сообщения) укладывается в уже существующее Phase-1 ограничение
"максимум один `.spawn` на модуль" — не требует его снятия.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Актор переживает захват DOM-замыканием (Priority: P1)

Разработчик спавнит актора в `старт()` и регистрирует DOM-обработчик,
захватывающий этого актора — программа компилируется в WASM AOT вместо
диагностики об отклонении.

**Why this priority**: без этого сама фича не существует — единственная
причина, почему захват сегодня отклоняется, устраняется здесь.

**Independent Test**: `старт()` спавнит актор, регистрирует
`DOM.на_клик`, захватывающий его — `zig build aot` компилирует без
`ctx.unsupported`.

**Acceptance Scenarios**:

1. **Given** `Процесс`, заспавненный в `старт()`, **When** DOM-замыкание
   захватывает его, **Then** компиляция проходит (не
   `AotUnsupported`).
2. **Given** та же программа, **When** `старт()` завершается, **Then**
   промоутший фрейм остаётся валидным (не указывает в область,
   которую следующий вызов перезапишет).

### User Story 2 - Обработчик реально общается с актором после возврата из `старт()` (Priority: P1)

Симулированный повторный вызов DOM-обработчика шлёт актору сообщение и
читает настоящий ответ — не нулевой/мусорный mailbox-слот.

**Why this priority**: промоушен без реальной обработки сообщения —
фича наполовину, не решает исходный мотивирующий случай (Elm-архитектура,
UI-события меняют состояние-модель).

**Independent Test**: реальный wasmtime-прогон — `старт()` вызывается
один раз (спавн + регистрация), затем WASM-обработчик вызывается ВТОРЫМ,
ОТДЕЛЬНЫМ вызовом (симулирует второй DOM-клик) — шлёт сообщение,
результат содержит настоящий ответ актора, не значение по умолчанию.

**Acceptance Scenarios**:

1. **Given** заспавненный и захваченный актор, **When** обработчик
   вызывается повторно (после того как `старт()` уже вернулся) и шлёт
   сообщение, **Then** актор обрабатывает его (раунды гоняются СРАЗУ
   после `отправить`, внутри тела обработчика — FR-003) и обработчик
   читает настоящий ответ.
2. **Given** та же настройка, **When** обработчик вызывается ТРЕТИЙ раз
   независимо от второго, **Then** актор по-прежнему в консистентном
   состоянии (предыдущий вызов не оставил повреждённый mailbox/frame).

### Edge Cases

- Актор не отвечает за отведённый лимит раундов (16, та же константа,
  что `scheduler_rounds`) — как при обычном таймауте `старт()`'s
  scheduler'а, `unreachable_term` ("превышен лимит раундов"), не тихий
  неверный результат.
- DOM-обработчик регистрируется, но ни разу не вызывается — промоушен
  не должен требовать хотя бы одного вызова хендлера (происходит один
  раз, при построении closure box'а, независимо от последующих
  вызовов).
- Несколько разных DOM-обработчиков захватывают ОДНОГО и того же
  актора — оба должны получить один и тот же (уже промоутнутый)
  указатель, не дублировать промоушен.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Typechecker/mir_lowering MUST принимать захват `Процесс`
  DOM-замыканием (убрать `.process => .unsupported` в
  `classifyCaptureDepth`), заменив его реальным промоушеном.
- **FR-002**: Промоушен MUST копировать весь frame-блок актора
  (`target_total_slots * 8` байт, включая инлайн mailbox) в permanent-
  регион (тот же механизм, что `promoteStructToPermanent`), не только
  заголовок/указатель.
- **FR-003**: `отправить(actor, сообщение)`, вызванный из тела
  DOM-обработчика (после возврата из `старт()`), MUST сразу же
  прогнать раунды актора (переиспользуя "process 1"-половину
  `emitSchedulerRound`, без process-0-половины) — сообщение
  гарантированно обработано до возврата из обработчика.
- **FR-004**: Лимит раундов при повторном входе MUST быть той же
  константой `scheduler_rounds` (16), что уже использует
  `buildScheduler` — не новая, отдельно настраиваемая величина.
- **FR-005** (пересмотрено при реализации — см. "Статус реализации"):
  раунды при повторном входе MUST гоняться до `scheduler_rounds` раз,
  но НЕ трапить, если шаг-функция актора так и не вернула `истина` —
  для персистентного актора (`выбор получить()`, каждая ветка
  хвостово рекурсирует в новый `получить()`) это НОРМАЛЬНОЕ,
  ожидаемое поведение навсегда, а не ошибка (см. ниже, почему
  исходная формулировка была неверна).
- **FR-006**: Существующее Phase-1 ограничение (максимум один `.spawn`
  на модуль, `старт()` обязан содержать `получить()`) остаётся БЕЗ
  ИЗМЕНЕНИЙ — не расширяется в рамках этой фичи.
- **FR-007**: Программы БЕЗ захвата `Процесс` DOM-замыканием (весь
  существующий actor-код) MUST компилироваться и выполняться идентично
  сегодняшнему — ноль регрессии.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Фикстура "спавн + DOM-замыкание захватывает актора"
  компилируется в `zig build aot` без `AotUnsupported`.
- **SC-002**: Реальный wasmtime-прогон — обработчик, вызванный ВТОРЫМ,
  отдельным вызовом после `старт()`, получает настоящий ответ актора,
  не нулевой/мусорный.
- **SC-003**: Существующий actor test suite (`aot_actors_test.zig`,
  `aot_actors_multiarg_test.zig`) остаётся зелёным без изменений
  ожидаемого поведения.
- **SC-004**: `zig build test`/`conformance`/`aot`/`lsp`/`browser` — все
  зелёные.

## Assumptions

- DOM-замыкание строится ПОСЛЕ `запусти`/`.spawn` в исходном коде
  (естественный порядок — сначала спавним, потом регистрируем
  обработчик, использующий актора) — промоушен в момент построения
  closure box'а безопасен, актор ещё не успел накопить состояние,
  которое нужно было бы переносить отдельно (mailbox инлайн в том же
  блоке в любом случае).
- Обработчик, захвативший актора, но не отправляющий ему сообщений —
  вне явного тестового покрытия (не требует прогона раундов вообще,
  FR-003 применяется только когда РЕАЛЬНО вызван `отправить`).
- Несколько НЕЗАВИСИМЫХ акторов (не один, захваченный многими
  обработчиками, а несколько РАЗНЫХ `.spawn`) — вне scope, покрыто
  FR-006 (ограничение остаётся).

## Статус реализации (2026-08-19)

**Сделано и проверено** (US1 — FR-001/002/006/007):

- `classifyCaptureDepth`'s `.process => .unsupported` → `.process =>
  .scalar` (`mir_lowering.zig`) — захват `Процесс` больше не
  отклоняется на этапе typecheck/lowering.
- `lowerDomClickClosure` ставит новый `mir.Module.
  actor_captured_by_dom_closure: bool` флаг при обнаружении
  `Процесс`-захвата (не зависит от происхождения — `.spawn` или
  `себя()`, различить их дёшево не удалось, см. ниже).
- `wasm_actors.zig`: И `expandSpawn` (фрейм заспавненного актора), И
  `buildScheduler` (frame0 = `старт()`'s собственный фрейм) при
  установленном флаге аллоцируют через `findOrBuildAllocPermanent`
  вместо обычной сбрасываемой арены — оба возможных источника захвата
  (`.spawn`-результат ИЛИ `себя()`) закрыты одним и тем же условием,
  без разбора происхождения значения (Phase-1's "максимум один
  `.spawn`" гарантирует не больше двух фреймов в модуле, оба
  покрыты).
- Regression: существующий тест "unsupported process capture" оказался
  на самом деле про `себя()` ВНЕ suspend-контекста (старт без
  `получить()`) — не про `.spawn`-случай вообще; переписан под
  реальное (по-прежнему честно отклоняемое, просто на другой стадии —
  `wasm_emit.zig`, не `mir_lowering.zig`) поведение.
- Новый тест на реальный `.spawn`-случай (простой fire-and-forget,
  `старт()` спавнит + ждёт первый ответ + регистрирует хендлер) —
  компилируется.

**Краш найден И ПОФИКШЕН** (независимый баг, не блокер больше):
попытка написать полный end-to-end тест (спавн + await первого ответа
в `старт()` + DOM-хендлер шлёт ВТОРОЕ, fire-and-forget сообщение) дала
краш (`thread panic: attempt to use null value`) в `wasm_actors.zig`'s
`rewireSuspendCalls`. Разобрано через debug-пробу (временный тест,
печать состояния на каждом шаге): реальная причина — не `type_store`
(как показалось по первой строке трейса), а `call.dst.?` — `is_i32`
считался БЕЗУСЛОВНО для КАЖДОГО `.call_builtin` внутри
CPS-suspending функции, ДО проверки, что имя вообще одно из 4
suspend-related (`mailbox_has`/`signal_has`/`mailbox_pop`/`signal_pop`).
`DOM.на_клик(...)` (void call_builtin, `dst = null`), зарегистрированный
ВНУТРИ уже суспендящегося `старт()`, попадал в тот же безусловный код —
гарантированный null-deref. Ни один прежний фикстур не комбинировал
"CPS-suspending функция" + "не относящийся к акторам void
call_builtin в том же теле" — баг был латентным, не связанным с этой
фичей конкретно, просто впервые задет ею. Фикс: computed `is_i32`
только внутри веток `mailbox_pop`/`signal_pop`, после проверки имени.
Тест на полный сценарий добавлен, компилируется, 49/49 в `zig build
aot`.

**Сделано и проверено** (US2 — FR-003/004/005):

- `wasm_actors.zig`'s `emitSendRoundDriving` — `отправить()` вызванный
  из тела DOM-обработчика теперь гоняет до `scheduler_rounds` (16)
  вызовов целевой шаг-функции актора сразу после постановки сообщения
  в очередь, прежде чем обработчик вернётся (`expandSend` получил
  новый параметр `round_driving: ?FunctionId`, `null` для `старт()` и
  для тела самого актора — обе уже покрыты другими механизмами).
- Реальный, найденный только на исполнении баг (не на чтении кода):
  первая версия трапила ("превышен лимит раундов"), если шаг-функция
  ни разу не вернула `истина` за 16 раундов. Оказалось, что `истина`
  у CPS-шаг-функции (`mir_cps.zig`'s собственный doc-comment) означает
  "функция ПО-НАСТОЯЩЕМУ завершилась", а не "сообщение обработано" —
  персистентный сервер-актор (`счётчик`: каждая ветка `выбор
  получить()` хвостово рекурсирует в новый `получить()`) НИКОГДА не
  возвращает `истина`, он просто снова суспендится, каждый раз,
  навсегда, by design. Значит трап срабатывал ДЛЯ ЛЮБОГО персистентного
  актора при любом сообщении через этот путь — 100% воспроизводимо, не
  крайний случай. Найдено разборкой скомпилированного `.wasm` через
  `wasm2wat` и сверкой со стек-трейсом `RuntimeError: unreachable` из
  Node (не одним чтением кода) — на этом стеке `@lambda_2` (сам
  обработчик) был САМЫМ ВНУТРЕННИМ кадром, то есть `call actor_step`
  каждый раз честно ВОЗВРАЩАЛСЯ (не трапил сам), и трапил именно МОЙ
  собственный "лимит раундов исчерпан" код. Фикс: убран трап целиком —
  `emitSendRoundDriving` гоняет раунды (останавливаясь ДОСРОЧНО только
  если шаг-функция ДЕЙСТВИТЕЛЬНО завершилась), но "осталась `ложь`
  после всех раундов" для персистентного актора — не ошибка, ровно тот
  же принцип, что `buildScheduler`'s собственный process-1 (спавненный
  фоновый актор) уже применяет: его `done1`, оставшийся `ложь`
  навсегда, никогда не был условием трапа, трапит только `done0`
  (`старт()`'а собственное завершение). Одного раунда достаточно для
  корректности в обычном случае — `mir_cps.zig`'s диспетчер после
  каждого `получить()` прыгает обратно к проверке почты НА МЕСТЕ (не
  через новый WASM `call`), так что один вызов шаг-функции уже
  обрабатывает как минимум только что отправленное сообщение;
  оставшиеся раунды — чисто защитный запас, не требование корректности.
- Новый сквозной regression-тест (`tests/wasm/aot_closures_test.zig`,
  "DOM.на_клик's отправить() actually drives the actor to process the
  message, not just enqueue it") — реальный прогон под Node/wasmtime
  (не просто проверка байт, как у более ранних тестов этой фичи):
  `старт()` спавнит + ждёт первый ответ + регистрирует обработчик,
  затем ОТДЕЛЬНЫЙ вызов `@invoke_click` шлёт актору сообщение и
  проверяет, что актор ДЕЙСТВИТЕЛЬНО произвёл наблюдаемый побочный
  эффект (`DOM.установить_текст`) до возврата из обработчика.

Все гейты зелёные: `test` (1814/1814), `conformance` (46/46), `aot`
(50/50), `lsp`, `browser`. US1 и US2 обе done — фича закрыта.

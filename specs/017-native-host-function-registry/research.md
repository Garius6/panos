# Research: нативный host-function registry для `внешний "хост"`

## Текущая архитектура (проверено по коду, не по докам)

`внешний "хост" функ имя(...)` — это ЧАСТНЫЙ случай общего `внешний`
FFI-механизма (`внешний.library == "хост"`), не отдельный путь. Три этапа,
все существующие уже сегодня:

1. **Резолв** (`resolver.zig:resolveForeignFunction`, ~строка 920-965).
   Для `"libc"`/`"хост"` на не-Windows уже есть спецкейс: вместо загрузки
   ОТДЕЛЬНОГО `.dylib`/`.so` по имени вызывается `dlopen(NULL, LAZY)` —
   POSIX-способ получить хендл на образ УЖЕ ЗАПУЩЕННОГО процесса (сам
   исполняемый файл + всё, что в него слинковано), затем `dlsym(handle,
   "имя_символа")`. Результат — `usize` адрес — кладётся в
   `Resolution.foreign_functions: AutoHashMap(SymbolId, usize)`.
   `pub export fn` + `rdynamic` в хост-приложении существуют ИСКЛЮЧИТЕЛЬНО
   для того, чтобы нужный символ вообще попал в таблицу динамических
   символов, которую видит `dlsym`.
2. **Компиляция** (`compiler.zig`) — резолвнутый `fn_ptr` (usize) +
   marshal-kinds параметров/возврата (`Целое(N)`/`Число(N)`/`КСтрока`/
   `ff_структура`/`Указатель(T)`, из `ast.ForeignMarshalKind`) упаковываются
   в bytecode-константу `bytecode.ForeignFunctionConstant` (`bytecode.zig`,
   ~строка 16) — `.call_foreign`-опкод ссылается на неё по индексу.
3. **Вызов** (`vm.zig:callForeign` → `invokeForeign`, ~строка 4665).
   Аргументы упаковываются (`packScalar`/`packStruct`) в сырые C ABI байты,
   `ffi_prep_cif`/`ffi_call` (libffi, `ffi_bindings.zig`) реально совершает
   вызов по `fn_ptr` как по чужому, заранее неизвестному C-указателю,
   результат распаковывается обратно (`unpackScalar`). CIF/layout/буферы
   кэшируются в VM на первый вызов каждой bytecode-константы — повторные
   вызовы не пересобирают cif, но каждый вызов всё равно идёт через
   универсальный `ffi_call`, не через прямой Zig `call`.

## Что это значит для встраивающего движка (jijka)

`внешний "хост"` УЖЕ работает и НЕ требует внешней `.dylib` — но платит две
цены, обе применимы к game-engine сценарию:

1. **Экспозиция символов.** Любая host-функция обязана быть
   `pub export fn` с `rdynamic` — это реальный публичный символ в таблице
   динамических символов итогового бинарника, виден `dlsym` кому угодно,
   не только резолверу panos. Для растущего API движка (десятки
   `game_*`-функций) это утечка деталей реализации в ABI исполняемого
   файла и потенциальное ограничение на LTO/strip.
2. **Оверхед на горячих путях.** `invokeForeign` всегда идёт через
   `ffi_call` — универсальный, рассчитанный на ПРОИЗВОЛЬНЫЙ незнакомый
   C ABI механизм. Для `внешний "хост"` сигнатура на самом деле известна
   Zig-компилятору движка НА ЭТАПЕ КОМПИЛЯЦИИ (это просто твоя же
   `pub export fn`) — платить цену полностью динамического FFI за вызов
   собственной, дружественной функции того же процесса — чистые накладные
   расходы. Существующий `--profile-ffi` (см. `docs/src/language/ffi.md`)
   существует именно потому, что это уже осознанная забота проекта для
   "графических циклов с десятками вызовов ... на кадр" — характерный
   паттерн FPS-движка (raycast/damage/transform каждый кадр на каждую
   активную сущность).

## Открытый вопрос из spec.md: форма Zig-API регистрации

`spec.md` (Assumptions) оставляет открытым: один вызов
`register(name, func)` на функцию vs один `comptime`-структ со всеми
функциями сразу. Решение ниже принято здесь (Phase 0), не откладывается
дальше.

- **Decision**: `comptime`-структ, переданный один раз через
  `Runtime.Config.host_functions`. Публичная функция-конструктор
  `panos.hostFunctions(comptime table: anytype) []const HostFunctionEntry`
  принимает анонимный структ вида `.{ .entity_apply_damage = fnPtr, ... }`
  (имя поля = имя, под которым функция видна в `.pns` через `внешний
  "хост"`) и на `comptime` строит массив `HostFunctionEntry`.
- **Rationale**:
  - FR-004 требует, чтобы несовместимая Zig-сигнатура была ошибкой
    КОМПИЛЯЦИИ движка — это естественно получается, только если весь
    набор функций проходит через `comptime`-код один раз, а не через
    рантайм-вызовы `register()`, где сигнатура стирается в `anytype`
    аргумент функции, вызываемой в рантайме (компилятор Zig создаёт под
    каждый `anytype`-вызов отдельную инстанциацию, но сам `register()`
    в рантайм-контексте не может провалить СБОРКУ движка при плохой
    сигнатуре так же чисто, как явный `comptime`-структ, вычисляемый
    один раз при инициализации).
  - Совпадает с существующим стилем `Runtime.Config` (уже
    структ-из-полей, передаваемый в `init` целиком — не через отдельные
    setter-вызовы после `init`), см. `zig/embed.zig:32`.
  - Один явный список читается как декларативная "точка входа" API
    движка — проще для code review, чем разбросанные по коду
    `runtime.register(...)`-вызовы (Simplicity First,
    `.specify/memory/constitution.md`).
- **Alternatives considered**:
  - `runtime.register("имя", func)` (рантайм-вызовы, по одному на
    функцию) — отклонено: сигнатура каждой функции стирается в границе
    рантайм-вызова, несовместимый Zig-тип обнаруживался бы только там,
    где `register` инстанцирует свой `anytype`-параметр — тот же
    механизм, просто размазанный по нескольким вызовам вместо одного
    структа; не даёт никакого выигрыша, только больше мест для ошибки
    (например, регистрация после `load()` — с одиночными вызовами это
    легче случайно сделать, чем с одним структом в `Config`).
  - Отдельный DSL/макрос-подобное описание API вне Zig (например, JSON/
    описание сигнатур в конфиге) — отклонено: сигнатуры и так есть в
    Zig-коде движка (сами функции), дублировать их в отдельном формате
    избыточно и рассинхронизируется (та же причина, по которой FR-004
    вообще требует именно `comptime`-проверку).

## Как VM зовёт зарегистрированную функцию, не используя libffi

Наивная идея "просто скастовать `fn_ptr: usize` в нужный Zig
function-pointer тип и вызвать" не работает В ОБЩЕМ СЛУЧАЕ: `vm.zig`'s
`invokeForeign` — ОДИН кусок рантайм-кода, обрабатывающий ЛЮБУЮ
зарегистрированную функцию с ЛЮБОЙ сигнатурой (число/типы параметров
известны только в рантайме, из `ForeignFunctionConstant.param_kinds`) —
именно поэтому существующий dynlib-путь вообще нуждается в libffi
(`ffi_call` умеет вызывать по сигнатуре, известной только в рантайме).

Решение — сдвинуть точку, где сигнатура становится известна, на этап
`comptime` РЕГИСТРАЦИИ, а не рантайм-вызова. `hostFunctions()` генерирует,
для КАЖДОЙ зарегистрированной функции, свой персональный
`comptime`-специализированный "тонкий" trampoline с ОДНИМ и тем же для
всех функций стёртым (type-erased) Zig-сигнатурой:

```zig
fn (args: []const value.Value) anyerror!value.Value
```

Тело trampoline (генерируется `comptime` через `inline for` по
`@typeInfo(@TypeOf(func)).@"fn".params`) распаковывает `args[i]` в
конкретный Zig-тип i-го параметра РЕАЛЬНОЙ функции (та же логика
преобразования, что `unpackScalar`/`packScalar` делают для C ABI байт,
только источник/приёмник — panos `Value`, не сырые байты), затем
`@call(.auto, func, args_tuple)`, затем упаковывает результат обратно в
`Value`. Указатель НА ЭТОТ trampoline (не на исходную `func`) — то, что
реально попадает в `HostFunctionEntry.call` и вызывается из
`invokeForeign`/новой `invokeNative` uniform'ым способом, независимо от
того, сколько разных сигнатур зарегистрировано. `ffi_prep_cif`/`ffi_call`
для этого пути не нужны вообще — единственная "универсальность" нужна
VM-стороне ровно на уровне "вызвать функцию с сигнатурой `([]Value)
!Value`", а это обычный Zig-вызов, не требующий рантайм-построения C ABI.

## Вывод

Действительно узкое, самостоятельное улучшение: НЕ новый синтаксис
`.pns`-стороны (`внешний "хост" функ ...` остаётся как есть, embedding.md
для скриптовой стороны не меняется), а альтернативный ИСТОЧНИК резолва +
альтернативный ПУТЬ вызова для случая, когда хост САМ регистрирует функцию
на Zig-стороне явно (а не полагается на то, что резолвер найдёт её через
`dlsym` по счастливому совпадению экспортированного имени):

- Резолв: `Runtime`/`Resolution` получает таблицу
  `имя → (fn_ptr, comptime-выведенная сигнатура)`, резолвер проверяет её
  ПЕРЕД `dlopen(NULL)`/`dlsym` для `foreign.library == "хост"`.
- Вызов: если constant помечена как "registry", `invokeForeign` вызывает
  `fn_ptr` напрямую с уже известной на этапе регистрации Zig-сигнатурой
  (без `ffi_prep_cif`/`ffi_call`) — переиспользуя те же marshal-kind
  правила, что уже есть для скалярных типов/`ff_структура`.
- Существующий `dlopen(NULL)`/`dlsym`-путь остаётся fallback — обратная
  совместимость с `tests/embed_host_test.zig` и любым текущим
  `pub export fn`-кодом без изменений.

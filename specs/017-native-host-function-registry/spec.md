# Feature Specification: Нативный host-function registry для `внешний "хост"`

**Feature Branch**: `017-native-host-function-registry`
**Created**: 2026-08-26
**Status**: Draft
**Input**: User description: "Путь скрипт → движок должен покрываться embed: регистрируем функции движка в embed и вызываем из скрипта — без `pub export fn`/`rdynamic`/dlsym, без libffi на горячем пути" (мотивирующий консьюмер — встраивающий FPS-движок jijka, см. `research.md`)

## Контекст

См. `research.md` для полной архитектурной вычитки текущего `внешний
"хост"`-пути. Резюме: он уже работает без отдельной `.dylib` (спецкейс
`dlopen(NULL)` на образ текущего процесса), но требует `pub export fn` +
`rdynamic` (экспозиция ABI-символов) и всегда вызывает через `ffi_call`
(накладные расходы универсального FFI на вызов на самом деле известной на
этапе Zig-компиляции сигнатуры). Эта фича добавляет альтернативный,
явно регистрируемый путь — не меняя ничего в уже задокументированном
скриптовом синтаксисе (`docs/src/architecture/embedding.md`,
`docs/src/language/ffi.md` — обе страницы актуальны и после этой фичи).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Регистрация host-функции без `pub export fn`/`rdynamic` (Priority: P1)

Встраивающее приложение (например, игровой движок на Zig) объявляет набор
Zig-функций и передаёт их в `Runtime` при инициализации — panos-скрипт
зовёт их через уже существующий `внешний "хост" функ имя(...)`, без единого
`pub export fn` и без флага `rdynamic` в `build.zig` встраивающего
приложения.

**Why this priority**: это единственная причина существования фичи —
устраняет требование публиковать ABI движка в таблице динамических
символов исполняемого файла ради scripting-моста.

**Independent Test**: `Runtime.init` с непустым набором зарегистрированных
host-функций, скрипт с `внешний "хост" функ scale(x: Число(64)) ->
Число(64)`, вызов через `Runtime.call` — возвращает корректный результат;
исполняемый файл теста собирается БЕЗ `rdynamic`.

**Acceptance Scenarios**:

1. **Given** `Runtime`, инициализированный с зарегистрированной
   Zig-функцией `scale(f64) f64`, **When** скрипт объявляет `внешний
   "хост" функ scale(x: Число(64)) -> Число(64)` и вызывает `scale(21.0)`,
   **Then** резолв проходит успешно и вызов возвращает `42.0`, без
   `pub export fn scale` и без `rdynamic` в тестовой сборке.
2. **Given** та же настройка, **When** имя в `.pns`-декларации не совпадает
   ни с одной зарегистрированной функцией и в образе процесса нет такого
   символа, **Then** резолв падает с тем же классом ошибки, что и сегодня
   (`Resolve Error: библиотека 'хост' не экспортирует символ '...'`) — не
   новый, отдельный текст ошибки.

### User Story 2 - Несовпадение сигнатуры ловится до выполнения (Priority: P1)

Разработчик по ошибке объявляет в `.pns` сигнатуру, не совпадающую с
зарегистрированной Zig-функцией (другое число параметров, другой marshal
kind) — получает понятную ошибку резолва, не крэш/UB/молчаливо неверные
данные в рантайме.

**Why this priority**: без этого registry опаснее существующего
`dlsym`-пути — там хотя бы отсутствие символа ловится до выполнения; здесь
несовпадение сигнатуры при неявном marshal'инге — единственный новый класс
риска, который вносит эта фича, и он обязан быть закрыт с первого среза.

**Independent Test**: зарегистрирована `fn add(i32, i32) i32`, скрипт
объявляет `внешний "хост" функ add(a: Число(64)) -> Число(64)`
(несовпадающее число параметров и marshal kind) — `Runtime.load`/`resolve`
возвращает диагностику, вызов не происходит.

**Acceptance Scenarios**:

1. **Given** зарегистрированная функция с N параметрами, **When**
   `.pns`-декларация объявляет `внешний "хост"` с другим числом параметров,
   **Then** резолв MUST вернуть `Resolve Error` с указанием имени функции
   и характера несовпадения — компиляция скрипта дальше не идёт.
2. **Given** та же функция, **When** `.pns`-декларация совпадает по числу
   параметров, но с другим marshal kind хотя бы одного параметра или
   возврата (например `Целое(32)` вместо `Число(64)`), **Then** резолв
   MUST вернуть `Resolve Error`, вызов не строится.

### User Story 3 - Вызов минует libffi на горячем пути (Priority: P2)

Игровой цикл зовёт зарегистрированную host-функцию (например, применение
урона или чтение transform) десятки раз за кадр — вызов идёт прямым
Zig-путём, не через `ffi_prep_cif`/`ffi_call`.

**Why this priority**: реальная мотивация встраивающего движка (jijka,
FPS) — не только удобство API, но и стоимость на кадр; без этого User
Story 1 даёт удобство, но не решает вторую половину исходной проблемы
(см. `research.md`, "Оверхед на горячих путях").

**Independent Test**: `--profile-ffi`-подобный замер (или прямой unit-тест
на количество вызовов `ffi_call` через инструментацию/мок в тестовом
сборе) показывает ноль обращений к `ffi_call` для registry-резолвнутых
вызовов при сохранении корректного результата.

**Acceptance Scenarios**:

1. **Given** зарегистрированная host-функция, **When** скрипт вызывает её
   N раз подряд, **Then** ни один из вызовов не проходит через
   `ffi_prep_cif`/`ffi_call` (проверяется на уровне реализации —
   `ForeignFunctionConstant`/аналог для registry-функций не содержит
   ffi-cif путь вызова).
2. **Given** та же настройка, **When** сравнивается с эквивалентной по
   сигнатуре `pub export fn`+`dlsym`-функцией на идентичной нагрузке,
   **Then** registry-путь не медленнее (замер, не строгий SLA — фича не
   должна регрессировать существующий путь, но и не обязана бить его на
   порядки).

---

### User Story 4 - Существующий `pub export fn`/`rdynamic`-путь не ломается (Priority: P1)

Проекты (в том числе `tests/embed_host_test.zig`), уже использующие
`внешний "хост"` через `pub export fn`+`rdynamic` без какой-либо
регистрации, продолжают работать без изменений.

**Why this priority**: это чисто аддитивная фича поверх работающего
механизма — регрессия здесь недопустима, `внешний "хост"` уже
задокументирован в `embedding.md` как публичный контракт встраивания.

**Independent Test**: `zig build test`/`zig build integration` без изменений
в `tests/embed_host_test.zig` проходят как сегодня.

**Acceptance Scenarios**:

1. **Given** `Runtime` без единой зарегистрированной host-функции, **When**
   скрипт объявляет `внешний "хост" функ имя(...)`, соответствующий
   реальному `pub export fn` в бинарнике, **Then** поведение идентично
   сегодняшнему (dlopen(NULL)/dlsym/ffi_call путь).
2. **Given** имя одновременно зарегистрировано в registry И существует как
   `pub export fn` в образе процесса, **When** скрипт вызывает эту функцию,
   **Then** используется registry-запись (явная регистрация имеет приоритет
   над случайным совпадением экспортированного символа — предсказуемость
   важнее «магии»).

### Edge Cases

- Регистрация после `Runtime.load()`/`compile()` (то есть после того, как
  резолв уже мог состояться для части графа модулей) — MUST быть либо
  запрещена (ошибка на уровне Zig API, `unreachable`/`error` из `register`),
  либо документирована как допустимая только строго до `load()`. Registry
  не проектируется как runtime-модифицируемый после старта резолва.
- `внешний "хост"` на wasm32-freestanding (браузерная сборка) — уже
  отклоняется на уровне `comptime`/`target_profile` (см. `research.md`) —
  registry НЕ вводит новое исключение из этого правила, ветка регистрации
  недоступна/no-op на freestanding так же, как весь остальной FFI.
- Zig-тип параметра/возврата регистрируемой функции не имеет однозначного
  соответствия ни одному marshal kind (`Целое(8|32|64)`/`Число(32|64)`/
  `КСтрока`/`ff_структура`/`Указатель(T)`) — MUST быть `comptime`-ошибкой
  Zig-компиляции самого встраивающего приложения (не рантайм-ошибка panos)
  — несовместимая сигнатура не должна была скомпилироваться вовсе.
- Два разных имени в registry с одинаковым Zig fn_ptr (одна и та же функция
  зарегистрирована под двумя именами) — MUST быть разрешено, это не
  конфликт (симметрично тому, что один и тот же C-символ может быть найден
  через `внешний` под любым локальным именем сегодня).
- Registry пуст (встраивающее приложение не регистрирует ничего) — MUST
  вести себя идентично сегодняшнему поведению (User Story 4) — нулевые
  накладные расходы на резолв при отсутствии регистраций (registry — не
  обязательный шаг встраивания).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `Runtime`/встраивающий Zig-код MUST иметь возможность
  зарегистрировать одну или несколько native host-функций (имя → Zig fn)
  до вызова `Runtime.load()`, не публикуя их как `pub export fn` и не
  включая `rdynamic`.
- **FR-002**: Резолв `внешний "хост" функ имя(...)` MUST сначала проверять
  registry по имени; при найденной записи резолв использует её и НЕ
  выполняет `dlopen(NULL)`/`dlsym`.
- **FR-003**: При отсутствии записи в registry для `foreign.library ==
  "хост"` резолв MUST падать обратно на существующий `dlopen(NULL)`/`dlsym`
  путь без изменений в поведении (FR не меняет семантику для
  незарегистрированных имён).
- **FR-004**: Регистрация MUST проверяться на этапе Zig-компиляции
  встраивающего приложения (`comptime`) — несовместимый Zig-тип
  параметра/возврата (не отображаемый ни на один существующий marshal kind)
  MUST быть ошибкой компиляции Zig, не рантайм-паникой panos.
- **FR-005**: Несовпадение `.pns`-декларации `внешний "хост"` и
  зарегистрированной Zig-сигнатуры (число параметров, marshal kind
  параметра/возврата) MUST давать `Resolve Error` того же класса, что
  существующие ошибки резолва `внешний` (диагностика с span, не
  крэш/`unreachable`).
- **FR-006**: Вызов registry-резолвнутой функции MUST не использовать
  `ffi_prep_cif`/`ffi_call` — прямой Zig-вызов через сохранённый указатель
  на функцию с сигнатурой, известной на этапе регистрации, переиспользуя
  существующие правила marshal'инга значений (`packScalar`/`packStruct`-
  эквивалент для входа, `unpackScalar`-эквивалент для выхода).
- **FR-007**: Существующий `pub export fn` + `rdynamic` +
  `dlopen(NULL)`/`dlsym` + `ffi_call` путь для `внешний "хост"` MUST
  продолжать работать без изменений, когда registry не задействован —
  ноль регрессии для `tests/embed_host_test.zig` и любого текущего кода
  встраивания.
- **FR-008**: Regisrty MUST быть недоступен (no-op/ошибка компиляции) на
  wasm32-freestanding таргете — тот же guard, что уже существует для
  `внешний` в целом (`comptime builtin.target.os.tag == .freestanding` /
  `target_profile != .native`).
- **FR-009**: Registry MUST быть областью видимости одного `Runtime`
  (не процесс-глобальный статический реестр) — несколько `Runtime`
  (например, последовательная загрузка нескольких уровней в одном
  процессе) с разными наборами host-функций MUST не влиять друг на друга.
- **FR-010**: При коллизии имени между registry-записью и реально
  существующим экспортированным символом с тем же именем в образе процесса
  (`pub export fn` + `rdynamic`), registry MUST иметь приоритет (см. User
  Story 4, Acceptance Scenario 2).

### Key Entities

- **HostFunctionRegistry**: таблица `имя (панос-идентификатор) →
  (указатель на Zig-функцию, marshal-сигнатура параметров/возврата)`,
  переданная/накопленная во время конфигурации `Runtime` до `load()`.
  Marshal-сигнатура выводится из Zig-типов параметров/возврата на этапе
  регистрации (`comptime`), используя тот же набор видов, что
  `ast.ForeignMarshalKind`.
- **ForeignFunctionConstant (расширение)**: существующая bytecode-константа
  `внешний`-вызова получает дискриминатор источника вызова (dynlib-адрес +
  libffi cif, как сегодня, ИЛИ registry-запись + прямой Zig-вызов) — оба
  варианта совместно живут в одном байткод-представлении `.call_foreign`,
  без нового опкода.
- **Resolver (расширение)**: `resolveForeignFunction` получает
  дополнительный источник поиска (registry), проверяемый ПЕРЕД
  `dlopen`/`dlsym`-веткой для `foreign.library == "хост"`; остальные
  библиотечные имена (`"libc"`, произвольные `.dylib`/`.so`/`.dll`) registry
  не касается.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Встраивающее приложение может вызвать panos-скрипт, который
  зовёт функцию движка через `внешний "хост"`, не имея в исходниках ни
  одного `pub export fn` и не включая `rdynamic` в `build.zig`.
- **SC-002**: Любое несовпадение сигнатуры между `.pns`-декларацией и
  зарегистрированной Zig-функцией обнаруживается на этапе `Runtime.compile()`
  (Resolve Error), 0% случаев доходят до рантайм-крэша/UB на этой почве.
- **SC-003**: Registry-путь вызова не содержит обращений к
  `ffi_prep_cif`/`ffi_call` — измеримо инструментацией/тестом на уровне
  реализации, не только "предполагается по дизайну".
- **SC-004**: 100% существующих тестов, завязанных на `внешний "хост"`
  (`tests/embed_host_test.zig`, любые FFI conformance/integration тесты),
  проходят без изменений в самих тестах.

## Assumptions

- Скриптовый синтаксис `внешний "хост" функ имя(...)` не меняется —
  фича целиком на стороне резолва/вызова, `docs/src/architecture/
  embedding.md` и `docs/src/language/ffi.md` остаются корректными без
  правок (кроме, возможно, добавления упоминания registry как
  альтернативы `pub export fn`, вне обязательного скоупа этой спеки).
- Ограничено native (non-freestanding) target-профилем — как и весь
  остальной `внешний`-механизм; браузерная песочница не приобретает и не
  теряет возможностей.
- Не расширяет набор marshal kinds (`Целое(8|32|64)`/`Число(32|64)`/
  `КСтрока`/`ff_структура`/`Указатель(T)`) — переиспользует то, что уже
  определено в `ast.ForeignMarshalKind`; функции с параметрами вне этого
  набора остаются недоступны для регистрации (симметрично тому, что они
  сегодня недоступны для `внешний` вообще).
- Мотивирующий консьюмер — встраивающий движок jijka (`../jijka/ROADMAP.md`,
  фаза 6 «Интеграция panos») — первый реальный потребитель API, но фича
  проектируется как часть публичного контракта `panos_embed`, не
  jijka-специфичный хак.
- Конкретная форма Zig-API регистрации (одна функция на вызов
  `register(...)` vs один вызов со структурой-таблицей всех функций сразу)
  — открытый вопрос уровня `/plan`, не фиксируется в этой спеке.
